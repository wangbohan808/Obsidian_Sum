## 1. 一句话定位（电梯陈述）

> 基于 Rockchip RK3588S 平台（Radxa ROCK 5C），从底层到应用独立完成了一套**只包含所需驱动的定制 Linux 发行版**，并在其上部署了端侧 AI 猫行为监控系统：实时识别"进食/饮水"事件并只录制有效片段，视频自动上传家庭 NAS 与云盘。

### 版本 A（技术深度向，适合嵌入式/驱动/BSP 岗）

```text
项目名称：基于 ROCK 5C 的定制 Linux 发行版与端侧 AI 猫行为监控系统
项目周期：约 3 个月（独立完成）

项目背景：
需要一套 7×24 运行的宠物监控设备：只在猫咪进食/饮水时录像，其余时间不录，
视频自动上传到家庭主机与云盘。要求系统镜像最小化、只含所需驱动，并集成端侧 AI。

职责与技术实现：
1. 系统构建：掌握并实践 Radxa 官方四条镜像构建路线——
   BSP（u-boot/内核 deb 打包）、Yocto（bitbake/recipe/layer）、
   Buildroot（rk3588_sdk 整包 update.img）、rsdk（mmdebstrap 组装 RadxaOS）；
   最终采用 BSP 定制内核 + rsdk 组装产出可烧录镜像，通过 --debs 集成自研 deb。
2. 内核与驱动：基于 6.1 内核做驱动裁剪（保留 MMC/USB/UVC/WiFi/NPU/MPP/RGA，
   裁剪蓝牙/PCIe/多余显示外设），通过 kconfig.conf 固化；编写并编译 MIPI CSI
   摄像头设备树 overlay（IMX219），配置 Media-Controller 媒体管线（rkcif/rkisp）；
   另支持 USB UVC 摄像头即插即用。
3. 端侧 AI：采集并标注真实场景数据集（3000+ 帧），微调 YOLOv8n 单类猫检测模型；
   用 RKNN-Toolkit2 完成 INT8 量化（校准集贴近夜晚/逆光场景），部署到 RK3588 NPU
   （RKNN-Lite2，单帧 <30ms）；设计"运动门控 → 检测 → 头部位置 ROI 判定 →
   时序状态机"流水线，区分进食/饮水/停留，事件识别准确率 92%+，日均误录 <10%，
   相比 7×24 录像节省约 96% 存储。
4. 模型优化：对比 YOLOv8n/s 与输入分辨率（640/416）的精度-延迟权衡；量化前后
   mAP 评估（<1% 损失）；尝试通道剪枝（NNCF）与稀疏训练（Rockchip AutoSparsity，
   明确 RK3576 平台限制并做方案取舍）；整理成 benchmark 报告。
5. 应用与运维：GStreamer + Rockchip MPP 硬件编码（H.264，CPU 近 0 占用），
   事件预录/续录缓冲，splitmuxsink 自动切段；systemd 服务化（看门狗、断网自愈、
   日志轮转）；SMB/NFS 挂载 + rsync 上传 NAS，rclone 上传 WebDAV/云盘；
   钉钉/Bark Webhook 事件通知；72 小时连续运行无重启。

成果：
- 完整可复现的构建流程（文档 + 脚本），镜像烧录即用；
- 误录率 <10%、漏录率 <5%、日均视频量 ~1.1GB（事件驱动）；
- 沉淀 4 条镜像构建路线、RKNN 量化部署、摄像头驱动移植等可迁移能力。
```

## 4. 面试高频问答（准备提纲）

### Q1：为什么最终选 rsdk 而不是 Buildroot/Yocto？

答：三者的本质区别是"rootfs 的组装方式"。rsdk 用 mmdebstrap 从 Debian 软件源组装，天然拥有 apt 生态——RKNN 运行时、GStreamer rockchip 插件、opencv 都是现成 deb，集成成本最低；Buildroot 从源码选配包，体积最小但移植 AI 栈工作量大；Yocto 可复现性最好但构建最重。项目要"快出可用系统"，所以 rsdk 主推，Buildroot/Yocto 作为能力储备各跑通了完整流程。

### Q2：如何区分"进食"和"停留"？

答：不是单帧分类，而是"空间 + 时间"两个维度的联合判定。空间上用检测模型拿到猫框，头部位置（或 pose 关键点）是否落在标定好的碗区/水区 ROI；时间上用状态机要求连续 N 帧命中才确认事件（防抖动）、连续 M 帧离开才结束（迟滞），再叠加运动能量门控过滤"睡觉/趴着"。这比纯分类器可解释、好调参，误报主要来自极端光照，用校准集贴近场景量化解决。

### Q3：INT8 量化损失多少精度？怎么做？

答：本项目用 RKNN-Toolkit2 做 PTQ，校准集 300~500 张真实场景帧，mAP 损失 <1%。关键是校准集必须贴近部署场景（夜视/逆光），量化算法从 normal 换 mmse，必要时对检测头做混合精度。如果还不行就上 QAT（量化感知训练），代价是训练成本。

### Q4：硬件编码怎么做的？CPU 占用多少？

答：RK3588 集成 VEPU 视频编码单元，通过 libmpp + GStreamer 的 mpph264enc 插件使用，720p/15fps 编码 CPU 占用接近 0。采集走 V4L2，缩放用 RGA 硬件，全链路避免 CPU 软编。

### Q5：MIPI 摄像头驱动移植都做了什么？

答：内核 sensor 驱动（IMX219）和 rkcif/rkisp 平台驱动本身已开启，缺的是板级设备树——ROCK 5C 的 DTS 没有 camera 节点。我参考同 SoC 的 EVB 与 5A/5B overlay，编写了 csi2_dcphy0 + I2C sensor 节点 + rkcif/rkisp 媒体管线的 overlay，并解决 GPIO（reset/pwdn/clk）与时钟绑定，用 media-ctl 验证拓扑后出图。

### Q6：断网/断电怎么办？

答：分层设计——视频先落本地盘再上传，上传脚本在目标不可达时静默退出等下轮重试（systemd timer 每小时），所以断网只积压不丢；上传用 rsync/rclone 支持断点续传；断电后 systemd 自启 + 看门狗兜底，splitmuxsink 按 5 分钟切段保证最多丢当前段。

### Q7：为什么不用 RKLLM 大模型？

答：本项目是低延迟视觉任务，LLM 不是必需。但我在文档里完整跑通了 RKLLM 的转换（DeepSeek-R1/Qwen2.5 1.5B → w4a16 .rkllm）与板端 Runtime 部署，把它作为"端侧 AI 能力矩阵"的一部分，可做后续的"猫行为问答/异常行为描述"扩展。
