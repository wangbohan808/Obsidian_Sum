# FreeRTOS 性质体验与源码阅读指南

面向本仓库 `CW32L010_APP` 当前实现：用 VS Code + CMSIS-DAP 调试，亲手观察**任务、优先级抢占、互斥锁、任务通知、队列**；再按路径读源码，弄清这些性质是如何落地的。

---

## 1. 先建立心智模型

裸机时代常见写法：

```c
while (1) {
    自检();
    解码();
    if (需要集尘) 集尘();
}
```

RTOS 把“一直占着 CPU 空转等待”改成“没事就阻塞，有事再跑”。本工程对应关系：

| 概念 | 本工程落点 | 你应感受到什么 |
|------|------------|----------------|
| 任务（线程） | `monitor` / `comm` / `dust` | 多个独立循环同时“活着”，但 CPU 同一时刻只跑一个 |
| 优先级 / 抢占 | dust=3 > monitor=2 > comm=1 | 集尘一唤醒，会打断低优先级任务 |
| 阻塞延时 | `vTaskDelay` / `vTaskDelayUntil` | 延时期间任务不占 CPU，Idle 或其它任务可运行 |
| 互斥锁 | `app_lock` / `app_unlock` | 持锁期间其它任务进不了同一临界区 |
| 任务通知 | `app_request_dust` ↔ `app_wait_dust_request` | dust 空闲时睡死在通知上，被点名叫醒 |
| 队列 | `app_evt_send` / `app_evt_recv` | monitor 生产事件，comm 消费事件 |
| 中断硬实时 | ATIM 100µs / SysTick 1ms 回调 | 红外、LED 仍走中断，不被任务调度拖慢 |

架构示意：

```text
                 ┌──────────── ATIM / SysTick ISR ────────────┐
                 │ 红外引导 / 极柱捕获 / LED / 1ms 业务        │
                 └────────────────────────────────────────────┘
                                      │
          ┌───────────────────────────┼───────────────────────────┐
          ▼                           ▼                           ▼
   [dust prio3]                [monitor prio2]              [comm prio1]
   等通知→集尘                  5ms 自检+喂狗                 1ms 解码
   ↑ xTaskNotifyGive            → 队列投递事件                 ← 队列取事件
          │                           │                           │
          └──────────── app_lock (递归互斥锁) ────────────────────┘
```

## 2. VS Code 怎么配、怎么开调

### 2.1 推荐扩展

- **CMSIS Solution / Arm CMSIS Debugger**（工程已用 `gdbtarget` + pyOCD）
- 能看变量、断点、Call Stack 即可；有 FreeRTOS 视图更好，没有也能用断点体验

### 2.2 启动调试

1. 接好板子与 CMSIS-DAP。
2. 编译：用 CMSIS 构建任务，或确保 `out/CW32L010_APP/.../CW32L010_APP.axf` 已是最新。
3. 运行与调试里选其一：
   - `CMSIS_DAP@pyOCD (launch)`：自动 Load + 起 gdbserver，适合从头烧录调试
   - `CMSIS_DAP@pyOCD (attach)`：已有 gdbserver 时附着
4. 配置会加载 **BootLoader 符号**，并 `add-symbol-file` 加载 **APP 符号**。业务断点请打在 APP 源文件（如 `CW32L010_APP/App/main.c`）。
5. Reset 后往往会停在 BootLoader 的 `main`；对 APP 的 `main` / `monitor_task` 下断点后 Continue，或直接对 APP 函数下断再复位运行。

### 2.3 调试面板常用项

- **断点（Breakpoints）**：本文所有实验的核心手段
- **变量（Variables） / 监视（Watch）**：观察 `need_duty`、`robot_at_dock_state`、`evt`、`xTickCount`
- **调用堆栈（Call Stack）**：看当前卡在哪个任务函数里
- **调试控制台**：可执行 GDB 命令（如 `info threads`，视工具链支持而定）

## 3. 六个动手实验（按顺序做）

每个实验：**先下断点 → Reset/Continue → 看停在哪、变量是什么 → 单步/继续对照预期**。

### 实验 A：确认三个任务都在跑

**断点：**

- `monitor_task` 里 `vTaskDelayUntil` 下一行（约 `base_self_detect` 前）
- `comm_task` 里 `pole_decoder_process` 一行
- `dust_task` 里 `app_wait_dust_request` 一行

**操作：** Continue 多次。

**预期：**

- 经常停在 `monitor` / `comm`
- `dust` 多半停在 `app_wait_dust_request`（阻塞等待），说明它在“睡觉”而不是空转 `while(1)`

**对照裸机：** 裸机没有“睡在 API 里”，只能轮询；RTOS 阻塞时 CPU 可去做别的事。

---

### 实验 B：周期任务 vs 相对延时

**断点：** `monitor_task` 的 `vTaskDelayUntil`；`comm_task` 的 `vTaskDelay`。

**Watch：** `xTaskGetTickCount()` 或全局 `xTickCount`（若符号可见）、`last_wake`。

**预期：**

- `monitor` 大约每 5ms 醒一次（`DelayUntil` 按绝对时间对齐）
- `comm` 每次业务后相对延时约 1ms

**源码意图：** `DelayUntil` 更适合固定采样；`Delay` 更简单，周期会随业务耗时漂移。

---

### 实验 C：任务通知 —— 叫醒 dust

**断点：**

1. `app_wait_dust_request` 内 / `dust_task` 调用处（等待侧）
2. `app_request_dust` 内 `xTaskNotifyGive`（发送侧）
3. `dust_task` 里 `dust_absorption_ctrl`（被叫醒后）

**如何触发发送侧（任选）：**

- 业务上触发“需要集尘”（上座且模式允许、或产测极柱逻辑）
- 或在调试器里：在 `app_request_dust` 调用点附近，确认 `need_duty` 被置 1 的路径

**预期顺序：**

1. dust 停在等待通知
2. 某任务走进 `app_request_dust` → `xTaskNotifyGive`
3. 下一步 Continue 后，dust 离开等待，进入集尘循环（高优先级）

**这就是“事件驱动”：** 没事件时 dust 不占 CPU；有事件时被精确唤醒。

---

### 实验 D：优先级抢占

**断点：**

- `comm_task` 的 `pole_decoder_process`
- `dust_task` 的 `dust_absorption_ctrl`

**操作：** 在 comm 停住时触发集尘请求，然后 Continue。

**预期：** 很快会进入 `dust_task`（prio 3），表现为高优先级打断低优先级——这就是抢占式调度。

**说明：** 若恰好都在延时/阻塞，也可能先看到其它路径；多 Continue 几次，结合 Call Stack 看当前任务函数名。

---

### 实验 E：互斥锁 —— 临界区互斥

**断点：**

- `app_lock` / `app_unlock`
- `monitor_task` 与 `comm_task` / `dust_task` 中持锁段

**操作：** 一个任务停在 `app_lock` 已拿到锁、正执行 `base_self_detect` 或 `dust_absorption_ctrl` 时，观察另一任务若也要 `app_lock`，会堵在 Take 上（再 Continue 后才会进去）。

**预期：** 同一时刻只有一个任务处于 `app_lock`…`app_unlock` 保护的业务段。

**注意：** 本工程用的是**递归互斥锁**。同一任务已持锁时再调 `app_request_dust()`→再次 `app_lock()` 不会自锁死；换普通 mutex 则会把自己卡死。阅读 `app_rtos.c` 时重点看这一点。

---

### 实验 F：队列 —— 生产者 / 消费者

**断点：**

- 生产：`monitor_task` 里 `app_evt_send`
- 消费：`comm_task` 里 `app_evt_recv` 成功后的 `(void)evt;` 行

**Watch：** `evt`（`APP_EVT_DOCK_ENTER` / `LEAVE` / `DUST_DONE`）

**操作：** 让机器人上座/离座状态变化（或在逻辑上制造 `robot_at_dock_state` 变化），再 Continue。

**预期：** monitor 先 `send`，随后某次 comm 循环里 `recv` 拿到同一类事件。

---

## 4. 源码阅读路线（由应用 → 内核）

按下面顺序读，不要一上来扎进整个 FreeRTOS 仓库。

### 第 1 层：应用怎么用 RTOS（必读）

| 文件 | 读什么 |
|------|--------|
| `CW32L010_APP/App/main.c` | 三个任务函数、优先级宏、静态创建、`vTaskStartScheduler` |
| `CW32L010_APP/App/app_rtos.h` | 对外 API 与注释中的三种原语 |
| `CW32L010_APP/App/app_rtos.c` | mutex / queue / notify 的具体封装 |
| `CW32L010_APP/App/FreeRTOSConfig.h` | 打开了哪些功能（mutex、notification、静态分配等） |

阅读提问清单：

1. 为什么 dust 优先级最高？空闲时它在干什么？
2. `app_request_dust` 做了哪两件事（改标志 + 通知）？
3. 为什么红外不放进任务而放在 `Timer_Task_Init` 注册的中断回调？

### 第 2 层：业务如何接到同步点

| 文件 | 读什么 |
|------|--------|
| `base_self_det.c` | 上座触发时改为 `app_request_dust()` |
| `func_pole_decoder.c` | 产测/集尘完成路径里的 `app_request_dust()` |
| `func_dust_collect.c` | `need_duty`、`dust_absorption_ctrl` 状态机（被 dust 任务调用） |
| `BSP/tim_cfg.c` | `SysTick_Handler`：先跑 1ms 业务，再转 FreeRTOS tick |

### 第 3 层：FreeRTOS 内核里“性质”怎么实现

工程实际链接的是：

`CW32L010_APP/Middlewares/FreeRTOS/`

建议精读（用“转到定义”跟着走）：

| 你用的 API | 跟进文件 / 符号 | 理解目标 |
|------------|-----------------|----------|
| `xTaskCreateStatic` | `tasks.c` | TCB + 栈如何绑在一起 |
| `vTaskDelay` / `vTaskDelayUntil` | `tasks.c` | 任务如何从 Ready 挪到 Delayed 列表 |
| `xTaskNotifyGive` / `ulTaskNotifyTake` | `tasks.c` | 通知值存在 TCB 里，为何比队列轻 |
| `xSemaphoreTakeRecursive` | `queue.c`（mutex 基于 queue） | 互斥如何记录持有者、如何阻塞等待者 |
| `xQueueSend` / `xQueueReceive` | `queue.c` | 环形缓冲 + 阻塞/就绪链表 |
| `vTaskStartScheduler` | `tasks.c` + `portable/GCC/ARM_CM0/port.c` | SysTick / PendSV 如何切上下文 |
| 上下文切换 | `port.c` / `portasm.c` | 为何任务切换最终靠 PendSV |

可选对照阅读（更完整注释的上游树，不参与编译也没关系）：

`CW32L010_APP/Resource/FreeRTOS-Kernel-main/FreeRTOS-Kernel-main/`

### 第 4 层：时钟与 tick 共存（本工程特例）

1. `FreeRTOSConfig.h` 把内核里的 `SysTick_Handler` 重命名为 `xPortSysTickHandler`
2. `tim_cfg.c` 提供真正的 `SysTick_Handler`：
   - `tick_ms_num++` → 业务 `timer_ms()`
   - `hal_timer_run(1ms)`
   - 调度器已启动则调用 `xPortSysTickHandler()`

读这一段是为了理解：**RTOS tick 与原有 1ms 业务如何共用同一 SysTick**，否则只读 `tasks.c` 会对不上板级行为。

## 6. 调试时常见现象与解释

| 现象 | 可能原因 |
|------|----------|
| 断点总在 BootLoader | 符号默认先停 Boot；对 APP 函数下断或 `add-symbol-file` 后 Continue |
| dust 一直不进集尘 | 未走到 `app_request_dust`；或通知在登记句柄前发出（本工程已在 `vTaskStartScheduler` 前 `app_rtos_set_dust_task`） |
| 进了 `vApplicationStackOverflowHook` | 某任务栈不够；可适当加大对应 `*_STACK_WORDS`（注意 4KB RAM） |
| 进了 `vApplicationMallocFailedHook` | 动态分配失败；本工程任务/锁/队列以静态为主，heap 很小属预期 |
| 单步时“跑飞”到奇怪地址 | 中断插入或优化；Debug 用 `-O0`，必要时在关键路径设断而非逐步跨过阻塞 API |

## 7. 建议的一周学习节奏

1. **第 1 天：** 只做实验 A/B，读完 `main.c` 三个任务  
2. **第 2 天：** 实验 C/D，读 `app_rtos.c` + `app_request_dust` 调用点  
3. **第 3 天：** 实验 E/F，对照 `queue.c` 里 mutex/queue 实现提纲  
4. **第 4 天：** 跟一次 `vTaskDelay` → Delayed 列表 → SysTick → 任务就绪的完整路径  
5. **第 5 天：** 读 `tim_cfg.c` + `port.c`，弄清 tick 与 PendSV  

学完后你应能用自己的话回答：

> 为什么 dust 空闲不空转？为什么集尘来了能打断解码？为什么共享状态要加锁？通知和队列各适合什么场景？

## 8. 和裸机对比（一句话收束）

- **裸机：** 时间靠你自己轮询和标志位，所有逻辑抢同一条 `while(1)`。  
- **本 RTOS 工程：** 时间片与阻塞由内核管；任务用优先级表达紧急程度；用锁保护共享数据；用通知/队列传递“发生了什么”，从而把“等”从忙等变成可调度的阻塞。

把第 3 节的六个实验在 VS Code 里各跑通一遍，再按第 4 节读源码，对 FreeRTOS 的“性质”会比只看文档扎实得多。
