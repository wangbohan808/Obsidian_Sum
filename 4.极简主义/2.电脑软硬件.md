# 电脑软硬件

## 硬件配置

- CPU：AMD Ryzen 9 9950X3D

## 存储分区哲学

> 可分离的内容全部放 D 盘，尽量减小 C 盘——前提是：删除 D 盘内容不影响系统使用。
> 这条前提是整个哲学成立的分水岭：不是"D 盘装得越多越好"，而是"D 盘永远不承载系统本体"。

### 三层边界（判定标准）

| 层 | 内容 | 位置 | 删除后果 |
|---|---|---|---|
| ① 系统本体 | Windows、驱动、服务、商店应用基建 | **永远 C** | 删了系统损坏 |
| ② 注册表绑定的软件 | 安装版程序 | `D:\Apps\<Name>` | 只废该软件，系统无恙 ✅ |
| ③ 纯数据/内容 | 代码/媒体/虚拟机/备份等九类 | D 盘其余分类 | 只丢数据，系统无感 ✅ |

哲学覆盖范围 = ② + ③。凡是让 D 盘内容滑入①层的操作，都违背哲学本身。

### 具体设置（Windows）

| 设置项 | 值 | 原因 |
|---|---|---|
| 新内容保存位置 → 新的应用 | **C:** | 设为 D 会在 D 盘生成 WindowsApps/WpSystem **系统托管目录**（滑入①层）。2026-08 的"找不到 Lenovo Vantage/存储设备已断开"事故根源即在此 |
| 新内容保存位置 → 文档/音乐/照片/影视 | **D:** | 纯内容③层，注册表 Known Folders 重定向，系统零依赖 |
| 新内容保存位置 → 离线地图 | **C:** | 系统位置服务组件，①层 |
| Win32 软件安装 | 手动指定 `D:\Apps\<Name>`（PascalCase、无版本号） | 安装器自己写注册表指向 D，删除只废该软件 |
| 绿色软件 | `D:\Portable\<Name>` | 无注册表，零系统耦合 |
| 应用数据（聊天记录/草稿/音色库） | 应用内设置迁到 `D:\Data\<Name>`；硬编码路径用 NTFS junction | junction 对应用透明、跨更新存活 |
| WSL / 虚拟机镜像 | `E:\Machines\WSL` / `D:\VM` | 只用 `wsl --export/import` 迁移，禁止运行中复制 vhdx |
| Chrome / Edge | 留 `C:\Program Files` | 官方安装器写死路径，合理例外 |

### D 盘十类目录（固定，禁止新增顶层）

`Apps` / `Portable` / `Games` / `VM` / `Code` / `Downloads` / `Media` / `Data` / `Backup` / `Desktop`

- 程序在 Apps，数据在 Data（如 `Weixin` 程序 / `WeChat` 数据）
- 安装包归档 `Downloads\Installers`，删重复前 SHA256 校验
- 一切清理动作 = 移入 `Backup` 而非直接删除

### 安全红线

1. **注册表登记的软件绝不直接移动/改名**——要换位置就"卸载 → 重装到 D:\Apps"，否则卸载/更新功能损坏
2. **绝不手改 MSI Installer 数据库与 StateRepository**——被移动软件的旧路径残留无害，批量改写才坏事
3. **系统缓存/组件库永不指到 D**——不用第三方瘦身工具搬 SoftwareDistribution，不对商店应用用"移动到 D 盘"

### 维护机制

- 每周日 09:00 只读路径体检（计划任务 `SystemPathAudit`），扫描注册表/快捷方式/服务中失效的 D 盘路径引用，持续验证"D 盘未出现拖累系统的内容"
- 变更口诀：**任何变更前先备份，任何变更后必验证**（应用启动 / 数据落位 / 快捷方式有效）

> 确立于 2026-08-24，源于 Lenovo Vantage"存储设备已断开"事故复盘：根因是当年"新应用保存到 D:"设置 + 磁盘整理清理了系统托管目录，最终引发 EFS 组件丢失、系统级连锁故障。已同步至 TRAE 全局记忆（user_profile.md）与 E:\ResetBackup_20260824 备份。

## 软件到底装在哪些位置（卸载的底层地图）

> 一次"干净卸载"＝把这 6 处里属于该软件的东西尽量清掉。
> 反过来，看懂卸载＝看懂一个软件被放到机器的哪些角落。

**1. 程序本体（安装目录）**
- `C:\Program Files` / `C:\Program Files (x86)`：真正的可执行文件、DLL、本体

**2. 注册表卸载项（元信息卡片）**
- `HKLM\...\Uninstall` 与 `HKCU\...\Uninstall`
- 存放"卸载地图"：软件名、厂商、安装路径、卸载命令
- ⚠️ Windows"设置→应用"和卸载工具，读的是同一张卡

**3. 用户配置与缓存**（最容易残留、也最容易被忽略）
- `%AppData%`（Roaming）：配置、登录态、sqlite/json 数据
- `%LocalAppData%`：缓存、数据
- 现代 Electron 软件（VSCode/Cursor 等）注册表记录极少，主要活在这里
- 卸载后默认留着 → 重装时配置/故障也会跟着回来（旧坏数据复现）

**4. 全局公共数据**
- `%ProgramData%`：机器级共享数据、授权
- ⚠️ 共用根目录（如 Adobe 公共授权），删错会误伤其它软件

**5. 用户外观层**
- 开始菜单快捷方式、桌面快捷方式

**6. 深藏的系统钩子**
- 系统服务、计划任务（ImagePath 指向该软件路径）
- 文件关联、CLSID 组件、Shell 扩展

### Geek 的清理哲学：启发式名字匹配，不是查表

> 核心认知：**注册表并不记录"AppData/ProgramData 里装了什么"**。
> Geek 靠的是第二步——用"软件名+厂商名"当关键词，去上面 1–6 处遍历，凡名字匹配就列为"疑似残留"，给你清单勾选。

**不是**：注册表存了路径 → 直接读取路径删除。
**而是**：读注册表拿元信息(软件名/厂商/旧路径) → 去各目录做**字符串名字匹配** → 猜出候选 → **你勾选确认**。

**匹配盲区（决定它漏扫/误报）**
- 文件夹名 ≠ 显示名（网易邮箱大师 vs `NetEaseMailMaster`）→ 漏扫
- 只会比名字，无法判断"独占数据"还是"共享公共数据" → 分支逻辑靠人
- 免费版不做"安装快照"（付费工具才有：装前快照、装后 diff），纯事后猜 → 必漏与少量误报

### 落地用法：日常排错三步

1. 软件首次异常 → 正常卸载重装，**先不碰 C 盘残留**，保留自己的配置
2. 重装后故障依旧 → 用 Geek 扫描，**重点删 AppData / ProgramData 下该软件自己的子文件夹**，顺带清注册表
3. 永不"全选删除" → 看一眼清单，**厂商公共根目录不勾，只勾软件自己的子文件夹**

> 风险边界：本体损坏用手动够用；AppData 内配置损坏（sqlite/json）才是 Geek 能提醒你追加清理的关键场景。

### 哲学对照（一句记忆）

Windows 自带卸载像搬家——家具搬走，抽屉杂物留在屋里。
Geek 像拿家具名字去各柜子搜相似盒子，全摆给你看、由你认领。

## WSL 与 VMware 重装系统后重建

> 适用场景：重装 / 初始化 Windows 后，E 盘残留的 WSL 发行版与 VMware 虚拟机数据还在，需要**让新系统重新接管这些旧数据**。
> 全程底线：**重装只清 C 盘，E 盘数据永不丢**——这正是"存储分区哲学"里"②③层可分离、系统本体留 C"的红利。

### 一句话记住

> **软件可以重装，数据舍不得。**
> 思路 = C 盘上程序/驱动/注册表全清掉重来（②层），E 盘上的 vhdx / vmdk 原样留下重新注册（③层）。

### 重装前必须确认的边界

| 项 | 在哪一层 | 重装后的命运 | 是否担心 |
|---|---|---|---|
| 系统本体、服务、商店应用 | ① 永远 C | 被清空 | 无所谓，本来就要重装 |
| VMware / WSL 的程序本体 | ② `D:\Apps\VMware` / C 内运行时 | 程序没了 | 重新装即可 |
| **WSL 发行版数据** | ③ `E:\Machines\WSL\*` | **原样保留** | 必须保住 |
| **VMware 虚拟机数据** | ③ `E:\Machines\VMWare\*`（注意是 `Machines` 中间层） | **原样保留** | 必须保住 |

> ⚠️ 路径里那个中间层最坑：虚拟机目录是 `E:\Machines\VMWare\Ubuntu_2204`，不是 `E:\VMWare\...`。按错了难免找不到残留数据。

### WSL 重建流程（保留 E 盘 vhdx）

**思路**：WSL 的程序（①层运行时）被清，但每个发行版的根文件系统 `ext4.vhdx` 在 E 盘 `E:\Machines\WSL\<发行版名>\ext4.vhdx` 完好。要做的只有两件事：**① 装回 WSL 运行时，② 把旧 vhdx 重新登记进新系统**。

**步骤**

1. 装回 WSL 运行时（管理员 PowerShell）
   ```powershell
   wsl --install --no-distribution   # 只装运行时，不装新发行版
   # 或补一次内核：wsl --update
   ```

2. 启用两个底层功能（二选一，最终都要生效）
   ```powershell
   Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Windows-Subsystem-Linux, VirtualMachinePlatform
   ```
   > ⚠️ **这步之后必须重启**。`VirtualMachinePlatform` 要重启后计算服务 `vmcompute` 才起来，否则 WSL2 报 `HCS_E_SERVICE_NOT_AVAILABLE`。

3. 把 E 盘旧 vhdx **原地登记**（不进 C 盘、不动原文件）
   ```powershell
   wsl --import-in-place Ubuntu-22.04 E:\Machines\WSL\Ubuntu-22.04
   ```
   - `--import-in-place` 会写一个新的注册指向旧 vhdx，**不复制 vhdx**，符合哲学里"只 export/import 迁移、禁运行中复制 vhdx"。
   - 每个旧发行版都这么登一遍。

4. 设为默认 + 验证
   ```powershell
   wsl --set-default Ubuntu-22.04
   wsl -l -v                     # 确认各发行版为 Version 2
   wsl -d Ubuntu-22.04           # 进入并看内核版本验证网络
   ```

**注意事项**
- 官方建议 WSL 本体装到 C（①层，删 D 不影响系统——它本来就该在 C）。
- **动手登记前先备份 vhdx**（拷一份到 `E:\Machines\WSL\_vhdx_backup_<日期>\`），万一登记出问题还能回滚。
- 内核版本确认正常 ≈ `6.x.x-microsoft-standard-WSL2`，DNS/网络正常即重建成功。

### VMware 重建流程（保留 E 盘虚拟机 + 装 D 盘程序）

**思路**
- 虚拟机的「数据」= E 盘 `Ubuntu_2204` 里的 vmdk/vmx/nvram → ③层，保留。
- 虚拟机的「程序」= VMware Workstation → ②层，重装到 `D:\Apps\VMware`（不装 C，不装 E）。
- **版本要匹配**：虚拟机 vmx 里的 `virtualHW.version` 决定需要哪个大版本。

### 版本判断（最容易踩的坑）

| 虚拟机 `virtualHW.version` | 需要的 Workstation | 例子 |
|---|---|---|
| 22（新硬件版本） | **25H2u1 一代（25.x / build 25219725+）** | 本次 `Ubuntu_2204` |
| 20 / 21 及更早 | 17.x | 装 17.6.4 即可 |

> 这次的教训：先按旧习惯装了 **17.6.4**，打开虚拟机没报错，但虚拟硬件版本 22 的 VM 在 17.x 下并不匹配 → **装对版本前先用文本编辑器看 vmx 的 `virtualHW.version`**。

### 安装

```powershell
# 官方静默安装，装到 D 盘（②层）
D:\Downloads\Important\VMware-Workstation-Full-25H2u1-25219725.exe /s /v"/qn EULAS_AGREED=1 INSTALLDIR=D:\Apps\VMware AUTOSOFTWAREUPDATE=0 /l*v C:\Windows\Temp\vmware_install.log"
```

### 若卸载旧版失败（1603 / 1725），如何安全强清残留

> 现象：旧版是"手填缺失源文件路径"硬装出来的，MSI 登记本身就是坏的（装数据库空 / 卸载 1725），正常卸载卸不掉、连 `msiexec /x` 都 1603。

安全强清清单（有条理，别乱删）：
1. 结束所有 VMware 进程（`vmware-tray.exe` / `vmware.exe` 会锁目录）。
2. 删除 VMware 相关服务：`sc delete VMAuthdService / VMnetDHCP / "VMware NAT Service" / VmwareAutostartService` 等（先 `Stop-Service`）。
3. 删除程序目录 `D:\Apps\VMware`。
4. 清 MSI 登记：删 `HKLM\...\Uninstall\{产品GUID}` 和 `HKLM\...\Installer\Products\{逆转GUID}`（按 DisplayName 匹配 VMware 再删）。
5. E 盘虚拟机数据全程不碰。

### 驱动版本不匹配修复（本次最关键的一步）

报错：
```text
Version mismatch with vmx86 driver: expecting 418.0, got 417.0.
Failed to initialize monitor device.
```
含义：程序已装成新版（25H2u1，要驱动 **418.0**），但 `C:\Windows\System32\drivers\vmx86.sys` **仍是旧的 417.0**——因为旧 `vmx86` 内核服务一直占用，25H2u1 安装时**跳过了装驱动**这一步。

修复要点（顺带讲清原理）：

| 环节 | 做法 |
|---|---|
| 找对驱动 | 从安装包解出 `Workstation.cab` → `_driver_vmx86_sys_Win8`（版本 `25.0.0.0 / 418.0`，100KB 左右） |
| 为什么不直接覆盖 | **内核驱动运行时 == 文件被锁定**，无法停（`sc stop` 报 1051 不支持停止控制） |
| 正确替换法 | 用 `MoveFileEx` + `MOVEFILE_REPLACE_EXISTING | MOVEFILE_DELAY_UNTIL_REBOOT`，把替换写进 `PendingFileRenameOperations`。Windows 会在下次**开机、驱动加载前**自动换成 418，一次重启即生效，无需二次操作 |
| 备份 | 覆盖前先把旧 417 拷一份到 E 盘，万一异常可回滚 |
| 验证 | 重启后 `Get-Item C:\Windows\System32\drivers\vmx86.sys` 版本应变为 25.0.0 / 418 |

> 记忆：**程序可卸载，驱动是"①层核心件"**——它永远在 C、且被旧服务占住时只能靠"重启前替换 + 重启加载"这套打法。这就是"软件搬得走、驱动得重装"的底层原因。

### 虚拟机文件夹清理对照（E 盘，别乱删）

| 文件 | 是什么 | 处理 |
|---|---|---|
| `Ubuntu-2204-64-bit-thin.vmdk` + `thin-s001~s044.vmdk` | **虚拟硬盘**（43 个 2GB 分片，共约 430GB）＝全部数据 | 🔴 绝对保留 |
| `Ubuntu-2204-64-bit.vmdk` | 硬盘描述文件，串联分片 | 🔴 保留 |
| `.vmx` / `.vmxf` / `.vmsd` / `.nvram` | 核心配置 / 附加配置 / 快照记录 / BIOS | 🔴 保留 |
| `Uuid.vmem` | **挂起时内存快照**（几十 GB） | 🟢 关机后删，可释放大空间 |
| `.lck` 目录 + `.lck\*.lck` | 运行时文件锁标记 | 🟢 关机后无意义，可删（运行中勿碰） |
| `autoinst.flp` / `autoinst.iso` | 装机自动应答介质，装完即废 | 🟢 可删 |
| `vmware*.log` / `mksSandbox*.log` / `*.scoreboard` | 日志 / 渲染缓存 | 🟢 可删 |

> ⚠️ 大磁盘被拆成几十个 2GB `.vmdk` **是 VMware 正常做法**，不是损坏，别误以为碎片。

### 踩坑复盘（本次全量经验）

1. **版本先看 vmx 的 `virtualHW.version` 再决定装哪个主版本**——省一次"装错→卸载→重装"。
2. **`--import-in-place` 只登记不复制 vhdx**，是保留 E 盘数据、也让系统接管它的唯一干净手段；登记前先备份。
3. **`VirtualMachinePlatform` 开了必须重启**，否则 WSL2 报 `HCS_E_SERVICE_NOT_AVAILABLE`。
4. **强制清坏的 VMware 残留**：进程→服务→程序目录→MSI 登记，四步有序来，数据目录全程不碰。
5. **驱动替换用 `PendingFileRenameOperations`（MoveFileEx 延迟重启）**：唯一能绕过"运行中驱动无法覆盖"的正规办法，一次重启生效。
6. **重装清空 C 盘不可怕**，因为①②③层哲学保证了——数据在 E、程序在 D，重装只丢系统本体。这就是分区哲学的复利。
