# 手机作音视频实验台：用 iPhone 学 Linux 音视频

> **一句话核心：iPhone 不是"便宜的相机"，它是一个「可控视频源 + 色彩基准 + 元数据样本库」——正因为它把传感器到输出的每一步都留了可读的痕迹，它比一台相机更适合学音视频工程。**
> **"器材太贵"是误判：你缺的不是相机，是一根 USB-C 转 HDMI 线加一个几十元的采集卡，而这两样本就在 [[音视频底层原理]] 第 3 步的清单里。**

> 定位：[[音视频底层原理]] 的**低成本实验台篇**。前者讲原理，本篇讲"用什么设备把原理变成可测数据"。
> 缘起：2026-11-11 提问"没有专业摄影器材，能否用 iPhone 学 Linux 音视频"。

---

## 零、结论先摆

| # | 判断 | 性质 |
|---|---|---|
| 1 | 能用，且**比相机更合适**：相机只给结果，手机给你可读的完整管线痕迹（元数据 + 格式可选 + 可复现） | 放行 |
| 2 | **"器材贵"是伪障碍**：真实缺口≈150 元（USB-C→HDMI 线 + 采集卡），不是一台相机的钱 | 换前提 |
| 3 | 三条路径价值不排序：**元数据路径（0 元）> HDMI 采集路径（150 元）> 手动拍摄路径（0 元但学不到光学）** | 排序 |
| 4 | 系统相机 app 会毁掉一切——计算摄影把物理关系打散了。**必须绕开**，飓风相机选对了 | 关键前提 |
| 5 | 手机的硬缺口只有三样：**光圈-景深-衍射链、真实噪点、镜头光学**。其余都能学 | 诚实边界 |
| 6 | 别为了学技术去拍。**样本拍摄（20 分钟）和爱好拍摄（3 小时）必须分开** | 真分歧 |

## 一、为什么手机反而比相机适合

相机的输出是"已经算好的结果"。手机的输出是"一条每一步都被标注了的管线"：

| 相机给你 | 手机给你 |
|---|---|
| 一个视频文件 | 一个视频文件 **+ 明确的色彩空间选项（SDR/HDR/Log）+ 帧率档位 + 编码格式 + 外置输出格式** |
| 想改色彩空间要换机器/换配置文件 | 设置里切一下，同一场景两组数据就出来了 |
| 变量难控（光线、镜头、滤镜） | **同一颗镜头、同一个场景，只改一个变量** |

对工程学习来说，**能控变量比画质好重要一个数量级**。这正是实验室和风景的区别。

## 二、路径一：元数据路径（0 元，性价比最高）

### 做什么

每拍一段就拷到 Linux，用 `ffprobe` 把它的"身份"读出来，再用 `ffmpeg` 转一道看丢什么。

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,level,width,height,r_frame_rate,pix_fmt,\
color_range,color_space,color_transfer,color_primaries,bit_rate,nb_frames \
  -of default=nw=1 input.mov
```

### 四个必做的对照实验

| # | 实验 | 改什么 | 你会亲眼看到什么 |
|---|---|---|---|
| 1 | **同场景，静止 vs 剧烈运动** | 只改内容 | H.264/HEVC 码率暴跌 vs 暴涨；**ProRes 几乎不变**（帧内编码）→ 把"码率是给变化花的"从结论变成观测量 |
| 2 | **SDR vs HDR（杜比视界）** | 设置里切 | `color_transfer` 从 `bt709` 变成 `arib-std-b67`(HLG) 或 `smpte2084`(PQ)，`color_primaries` 变 `bt2020`。**BT.2100 的纸质概念变成一行动词** |
| 3 | **Log 开 vs 关** | 飓风相机里切 | 同一个 transfer 字段，两种曲线；暗部数据量明显不同 → 理解"Log 不是滤镜，是把线性光重新分配编码位" |
| 4 | **ProRes vs HEVC** | 设置里切 | 文件体积差一个数量级，但画质差距远小于体积差距 → 理解"帧内编码买的是可编辑性，不是画质" |

### 这一步为什么最值钱

机器人视觉和端侧 AI 的所有前端问题，本质都是**"这块数据是什么格式、什么范围、什么色彩空间"**。
`ffprobe` 的输出就是这些问题的标准答案格式——**面试时能说出"我读得懂一段视频的元数据"，比"我调过参数"硬得多。**

> [!tip] 顺手能建立的直觉
> 拍一段 HDR 视频，用 ffmpeg 直接丢进不支持 HDR 的播放器 → 画面发灰发暗。
> 这就是 [[音视频底层原理]] §二 那个"Limited 当 Full 显示"的**同族故障**，只是发生在 HDR→SDR 的色调映射上。
> 见过一次，以后看到"灰蒙蒙"就知道该查元数据而不是调亮度。

## 三、路径二：HDMI 采集路径（≈150 元，最高工程价值）

### 器材

| 件 | 价格量级 | 说明 |
|---|---|---|
| USB-C → HDMI 转接头/线 | 30–80 元 | iPhone 15 起全系支持 USB-C DP Alt Mode，可输出到外接显示器 |
| HDMI → USB 采集卡 | 50–150 元 | 选 UVC 免驱的，Linux 下直接出 `/dev/video0` |

**这就是 [[音视频底层原理]] §0.4 第 3 步"换成采集卡 + HDMI"的全部成本**——他本来就该买。

### 为什么这条路径价值最高

它把 §三（HDMI/UVC）、§一（格式协商）、§二（色彩范围）三节同时变成可操作的东西：

| 要验证的问题 | 怎么测 | 对应章节 |
|---|---|---|
| 采集卡是否透传 color range？ | `v4l2-ctl --get-fmt-video` 看 `quantization` 字段 | §二 warning 块 |
| iPhone 输出 DP 时是 Full 还是 Limited？ | 采一帧，取一个纯白块看灰度值是 235 还是 255 | §二 |
| 为什么采集卡要"装成显示器"？ | 拔掉采集卡的 HDMI 输入，看 iPhone 是否提示"无显示器" | §三「采集卡在协议上是 sink」 |
| 格式协商怎么发生的？ | `v4l2-ctl --list-formats-ext` 对比 iPhone 支持与卡支持 | §0.3 疑问 3 |
| HDCP 撞墙长什么样？ | 播放受保护内容时采集卡黑屏，普通界面正常 | §三 HDCP |

> [!important] 这才是"能写进简历的实测数据"
> 不是"我会用 OBS"，而是：**"iPhone 作为 HDMI source 接 UVC 采集卡，实测输出为 limited range 4:2:2，
> 而采集卡驱动未透传 quantization 字段，导致 Linux 侧按 full range 解释，画面被压暗约 12%（235/255），
> 需在 ffmpeg 侧显式加 `-color_range` 修正。"**
> 这一句话同时命中了格式、范围、驱动行为、修正手段——比任何"熟悉音视频"的自述都硬。

### 风险（本身就是教材）

- **可能黑屏**：部分采集卡对 iPhone 的 EDID 应答处理有问题，或触发 HDCP。**测不通也是收获**——它证明了 §三 那句"便宜卡兼容性差的根源就是省了 EDID/HDCP"。
- **可能有延迟**：这正好对应 §六 的延迟构成。
- 备选方向：有 app 让 iPhone 直接作 UVC 设备（免采集卡），需要在 iOS 侧确认可用性与授权，**未验证，列为待办**。

### 落地命令

```bash
v4l2-ctl --list-devices                       # 卡在不在
v4l2-ctl -d /dev/video0 --list-formats-ext    # 拿得到哪些格式
v4l2-ctl -d /dev/video0 --get-fmt-video       # 看 pixfmt 与 quantization
ffmpeg -f v4l2 -i /dev/video0 -t 10 -c:v copy test.mkv   # 先录原始流，别转码
gst-launch-1.0 v4l2src device=/dev/video0 ! \
  video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1 ! \
  mpph264enc rc-mode=cbr bps=8000000 ! h264parse ! flvmux ! rtmpsink location="rtmp://..."
```

最后一行接上 §八——**此时你的"直播"是用手机当摄像机、Rock 5C 当编码器，和 OBS 走的是同一条链路。**

## 四、路径三：手动拍摄路径（学摄影，学不到多少工程）

### 飓风相机选对了，但要知道它为什么对

它真正的价值不是"能调参数"，而是**把计算摄影的干预降到最低**：

| 它给的 | 为什么重要 |
|---|---|
| 手动快门 / ISO / 白平衡 | 系统相机替你决定的一切，这里交回手里 |
| **直方图 + 波形图** | 曝光判断从"看着差不多"变成"读数据"——这是摄影里唯一能自检的部分 |
| Log 直出 + 实时 LUT | 取景框里看到的是**套 LUT 后的预览**，文件里存的是**未套的 Log**。这个二分本身就在教你"显示变换 ≠ 数据" |
| Open Gate 画幅 | 理解"画幅/裁切"不是审美，是分辨率与像素总量问题 |

> [!warning] 它的"光圈"是模拟的
> 官方描述写明"光圈（**模拟**）"。iPhone 摄像头是固定物理光圈，app 里的 f/1.4–f/16 只是**调节曝光量的等效值**，
> 不改变景深、不改变衍射。**所以在手机上永远学不到"光圈-景深-衍射"这条链**，这是硬缺口。
> 可以学到的替代项：**快门角**（25 fps → 1/50，180° 法则），这条对视频工程是真知识（运动模糊与帧率的关系）。

### 一个关键确认

**系统相机 app 必须停用。** 它的 Deep Fusion / 光像引擎会把你调的一个参数，变成算法的一整套决策。你调的是"输入"，看到的是"苹果的答案"——**这不是光学，是苹果的算法，学它等于学 iPhone 而不是学图像**。

## 五、ProRes RAW：这台手机上最值钱的东西（仅 Pro 机型）

如果手上是 17 Pro，**ProRes RAW 是你通向 ISP 的钥匙**。

| 层级 | 数据状态 |
|---|---|
| ProRes RAW | **12-bit Bayer 原始数据**：没去马赛克、没白平衡、没降噪、没色调映射 |
| Apple Log 2 | 已过 ISP，但保留了宽动态范围 |
| 普通 HEVC | ISP 全部算完（含计算摄影） |

**这三级正好是 ISP 管线的三段横切面。** 拿同一场景拍三份，逐级看差异，你就把"去马赛克 → 白平衡 → 3A → 色调映射 → YUV 输出"这条链**从名词变成了观察**。

> [!important] 这就是机器人视觉的前端
> **你手机里的 ProRes RAW ≡ 你板子上 ISP 的输入。**
> RV1106 / RK3588 的 ISP 做的事，和 iPhone 把 Bayer 变 HEVC 做的事，前半段是同一套（demosaic、AWB、AE、gamma）。
> 学这一段，等于同时在学摄影、学音视频、学端侧 AI 视觉——**这才是"爱好与工作合流"里那条真正实心的桥**（见 [[33.爱好与技术合流·两条不对称的桥]] §二）。

如果手上是标准版 17：没有 ProRes RAW，但**路径一、二完整可用**，只是少这一层。这一层可以等以后有需求再补，不影响任何入门。

## 六、手机学不到的三样（诚实清单）

| 缺口 | 为什么补不了 | 什么时候再补 |
|---|---|---|
| **光圈-景深-衍射** | 固定物理光圈，app 里的光圈值是模拟 | 真要拍人像/微距作品时；对求职无用 |
| **真实噪点与 ISO 增益** | ISP 降噪把噪点抹平了，看到的不是传感器的信噪比 | 只在做低照度视觉标定时才需要（那时用板子上的传感器，不用手机） |
| **镜头光学**（畸变、暗角、色散、镀膜眩光） | 手机镜头是计算校正过的，且不可换 | 无需求。这是摄影爱好者的需求，不是音视频工程师的 |

> 三样缺口的共同点：**它们都属于"摄影"这门手艺，不属于"音视频工程"这门技术。**
> 所以缺口存在，但不构成障碍——**你要学的东西恰好全在手机覆盖范围内**。

## 七、真分歧：别为了学技术去拍

这条接 [[33.爱好与技术合流·两条不对称的桥]] §四：**技术→爱好免费，爱好→技术有成本。**

| | 样本拍摄 | 爱好拍摄 |
|---|---|---|
| 目的 | 产出可测数据 | 松下来、拍好看 |
| 时长 | 20 分钟，固定机位、固定场景、只改一个变量 | 3 小时，随便走 |
| 判据 | 有没有拿到对照 | 有没有松下来 |
| 器材 | 三脚架、一张灰卡、固定光照 | 手持即可 |

**两种必须分开记。** 一旦"出去拍照"变成"顺便采集数据集"，它就同时当不成燃料也当不成爱好了——和 `30` 里"游戏写成修炼"是同一个坑。
