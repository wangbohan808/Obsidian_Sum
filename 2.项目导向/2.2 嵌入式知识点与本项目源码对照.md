### 2. C++ RAII：资源获取即初始化

#### 2.1 概念

RAII（Resource Acquisition Is Initialization）：把资源生命周期绑定到对象生命周期。

- 构造时获取资源（加锁、打开文件、分配内存）
- 析构时自动释放（解锁、关文件、释放内存）
- 即使函数中途 `return` / 抛异常，栈展开也会调析构函数 → **不易漏释放**

#### 2.2 源码：锁的 RAII

`timer_tactics.cpp` 注释写得很直白：

```299:301:service/timer_tactics.cpp
void TimerTactics::CompatibleTimeZones(const int i_zone, const int i_zone_min) {
    std::lock_guard<std::mutex> lock(zone_mutex_);   // 自动加锁和解锁
```

等价于：

```cpp
zone_mutex_.lock();
// ... 业务
zone_mutex_.unlock();   // 若中间 return，容易漏 unlock → 死锁
```

用 `lock_guard` 后，函数任意退出路径都会解锁。

同类用法遍布：

- `protocol_adapter/haier_adapter.cpp`：`write_mutex_`、`sendCloudFile_mutex_` 等
- `service/dev_status.cpp`：`status_mtx_`、`cmd_mtx_`
- `service/path.cpp`：`unique_lock`（需要临时解锁时用它）

#### 2.3 新手练习

在任意 `service/*.cpp` 里找一处 `lock_guard`，故意在中间加 `return`，确认不会死锁——这就是 RAII 的价值。

### 3. 自动释放内存 & 动态内存管理

#### 3.1 底层逻辑（简化）

用户态动态内存大致路径：

```
new / malloc
  → 用户态堆分配器（glibc ptmalloc / jemalloc 等）
  → 必要时 brk/mmap 向内核要虚拟内存
  → 返回可用地址

delete / free
  → 归还堆；不一定立刻还给 OS
```

嵌入式注意点：

- 大块地图缓冲（本项目常申请 `1024*1024`）容易造成堆碎片
- 交叉编译目标内存紧张，泄漏会慢慢拖死进程

#### 3.2 源码：裸 `new/delete` vs 智能指针

`map.cpp` 同时出现两种风格：

### 4. 内存泄漏真实场景（本仓库教学级案例）

#### 4.1 问题模式：异步回调 + 超时提前返回

`protocol_adapter/haier_adapter.cpp` 把异步 OSS 上传封装成阻塞接口：

```51:102:protocol_adapter/haier_adapter.cpp
bool uhsd_push_file_to_oss_blocking(...) {
    // ...
    auto *cb_param_ptr = new CallbackWrapper(promise_ptr);

    int call_result = uhsd_push_file_to_oss(..., cb, cb_param_ptr);

    if (call_result != 0) {
        delete cb_param_ptr;   // 调用失败：正确释放
        throw std::runtime_error(...);
    }

    if (result_future.wait_for(timeout) == std::future_status::ready) {
        result = result_future.get();
        return true;           // 成功路径：回调里 delete
    } else {
        return false;          // 超时：此处未 delete！
    }
}
```

**泄漏条件**：接口调用成功，但超时返回 `false`，而回调稍后才到达（或永不到达时更糟）。

- 若回调最终到达：`delete wrapper_ptr` 仍可能发生（不一定泄漏堆），但 `promise` 已过期，`set_value` 可能异常（代码用 `try/catch` 吞掉）
- 若回调永远不来：`cb_param_ptr` 永久泄漏

同类模式还出现在删除云文件、实时地图更新的 blocking 封装中。

#### 4.2 改进思路（学习用）

1. 用 `shared_ptr` + `weak_ptr` 管理回调参数，避免裸 `new`
2. 超时后置「已取消」标志，回调里检查后再 `set_value`
3. 或统一用带生命周期的对象（RAII）托管 `cb_param`

这正是「知道 RAII / 异步生命周期」后能修的真实 bug 类问题。

### 5. 多态与虚函数表（vtable）

#### 5.1 概念

- **多态**：同一接口，不同派生类有不同实现；通过基类指针/引用调用时，运行时绑定到真正派生类函数。
- **虚函数表（vtable）**：编译器为含虚函数的类生成函数指针表；对象里通常有隐藏的 `vptr` 指向该类的 vtable。调用 `p->foo()` 时变成「查表再跳转」。

注意：多态是语言/设计概念；vtable 是常见实现机制。二者不是对立关系，而是「能力 vs 实现」。

- 纯虚函数 `= 0` 使基类成为抽象类，不能直接实例化。

### 7. 并发竞争问题及解法

#### 7.1 什么是竞争（Race）

多个线程无同步地读写同一共享数据，结果依赖调度顺序 → 数据损坏、偶现 bug、难复现。

本项目典型共享资源：

- 设备状态结构（`DevStatus`）
- 上传/写云文件路径（`haier_adapter` 多个 mutex）
- 地图/路径缓冲（`map`/`path`/`multi_map`）

正确防护示例（命令路径加锁）：

```cpp
// service/dev_status.cpp 模式
std::lock_guard<std::mutex> locker(cmd_mtx_);
// 再执行 CallServer / 改状态
```

`haier_adapter` 对不同资源用不同锁，降低锁粒度、减少互相阻塞：

```178:181:protocol_adapter/haier_adapter.h

```

#### 7.2 教学反例：`MsgQueue::Push` 的长度更新

```41:51:third_party/apos_common/include/apos_common/msg_queue.h
void Push(T &msg) {
    if (length_ >= size_)
        throw MsgQueueEmptyException();
    if (is_finished_)
        return;
    mutex_.lock();
    msg_queue_.push_back(msg);
    mutex_.unlock();
    length_++;          // 在锁外自增
    sem_.Post();
}
```

问题点：

1. `length_` 检查与入队不在同一原子临界区 → 可能超容量入队
2. `length_++` 虽是 `atomic`，但「检查 + 修改」整体不是原子事务
3. `is_finished_` 非原子，与 `Destroy` 并发时有可见性问题

**解法原则**：共享状态的「读-改-写」整段放进同一把锁；原子变量不能替代对复合不变量的保护。

#### 7.3 实用排查清单

1. 偶现崩溃 / 偶现错误值 → 先怀疑竞态
2. 用 ASan / TSan（ThreadSanitizer，若工具链支持）抓数据竞争
3. 所有跨线程可见的成员变量：要么锁保护，要么明确无共享
4. `detach` 线程要注意对象生命周期（`this` 是否已销毁）

本仓库大量 `std::thread(...).detach()`（如配对成功后上传资源），务必保证单例生命周期长于线程。

### 9. 「工作队列能否休眠」在本项目中的对应物

内核 workqueue：跑在内核线程上，**可以 sleep**，属于进程上下文（内核线程语境）。

本仓库没有 `schedule_work` / `tasklet`，但有等价用户态模式：

- `std::thread` 里做耗时上传、状态刷新
- `main` 循环 `sleep_for`
- `future.wait_for` 等待回调

这些线程都在进程上下文，**可以休眠**。  
若某天你写内核驱动，才需要区分：ISR / softirq / tasklet 不能 sleep；workqueue 可以。

### 11. 优先级反转（概念 + 本项目现状）

**优先级反转**：高优先级线程等低优先级线程持有的锁，而中优先级线程抢占低优先级 → 高优先级被间接饿死。

本项目：

- 应用层主要是普通 `std::mutex`，无优先级继承
- Vendor 线程 API 有 `SCHED_RR` / priority 字段（OSDK POSIX 封装）

对用户态联网进程，多数情况公平调度即可；若以后做实时控制线程 + 普通日志线程抢同一把锁，才需要认真对待（优先级继承协议、避免长时间持锁）。

## 第三部分：领域补充（本仓库几乎没有，但嵌入式必学）

> 这些知识点不在本用户态工程里落地，但同产品板上的 WiFi/传感器/电源驱动会用到。下面给「够用」的概念版，方便你和驱动同事对词。

### 12. 中断上下文 vs 为什么中断里不能休眠

| | 进程上下文 | 中断上下文 |
|--|------------|------------|
| 谁在跑 | 某个进程/内核线程 | 硬件中断处理程序（ISR） |
| 能否 sleep | 可以 | **绝对不行** |
| 能否拿可能睡眠的锁 | 可以（注意死锁） | 只能用 spinlock 等 |
| 能否调度切换 | 可以 | 不能随意调度 |

**不能 sleep 的原因（直觉版）**：

1. 中断打断了任意进程；若 ISR 里 sleep，内核不知道「该把谁的睡眠账记给谁」
2. 中断需要尽快返回，否则丢中断、拖垮实时性
3. 睡眠依赖调度器；中断路径禁止调度

正确做法：ISR 只做「确认硬件 + 记标志 + 唤醒底半部」，重活放到软中断 / tasklet / workqueue。

### 13. DMA：是什么、为什么要用

DMA（Direct Memory Access）：外设与内存之间由 DMA 控制器搬数据，**不占用 CPU 逐字节拷贝**。

用途：WiFi 收发包、摄像头、音频、大块 SPI/存储传输。  
本联网进程不直接编程 DMA；你看到的高速吞吐通常发生在内核驱动里。

### 14. IIC（I2C）读写错误怎么排查

典型步骤：

1. 示波器/逻辑分析仪看 SCL/SDA 波形、上拉、地址 ACK
2. `i2cdetect` / `i2cdump` 确认从设备是否在总线上
3. 查是否地址 7bit/8bit 搞反、时序过快、多主冲突
4. 驱动返回值：`-ETIMEDOUT` / `-EREMOTEIO` / `-ENXIO` 分别对应超时、NACK、无设备
5. 确认电源域、复位脚、复用脚配置

本仓库仅在蓝牙 HCI 枚举里出现 `HCI_I2C` 字样，无业务 I2C 读写。

### 15. 驱动模块 panic 怎么调试

1. 串口抓完整 oops/panic 日志（含 Call Trace）
2. `addr2line` / `gdb vmlinux` 把 PC 翻成源码行
3. 区分：空指针、栈溢出、调度违规（sleep in atomic）、锁问题
4. 用 `BUG_ON`/`WARN_ON`、动态 debug、`ftrace` 缩小范围

用户态对应物是：进程崩溃 + core + GDB；不要和内核 panic 混为一谈。

### 16. rundump / kdump

- **kdump**：内核崩溃时切换到 dump 捕获内核，把内存写出（vmcore），再用 `crash` 分析
- 部分厂商/平台会有 rundump、ramdump 等同类崩溃转储方案

本仓库无相关逻辑；设备整机死机时由系统/BSP 团队处理。

### 17. 中断底半部：tasklet 与工作队列

| | softirq/tasklet | workqueue |
|--|-----------------|-----------|
| 上下文 | 原子/软中断（偏中断侧） | 内核线程（进程上下文） |
| 能否 sleep | 否 | **是** |
| 适用 | 短、不可睡眠的延迟处理 | 可睡眠、可阻塞的重活 |

用户态对照：本项目的 `detach` 工作线程 ≈ 「把重活丢到可睡眠上下文」。

### 18. 驱动能直接访问用户空间内存吗？

**不能直接乱访问。** 用户态指针对内核没有稳定映射意义（进程切换后失效）。

正确间接访问：

- `copy_from_user` / `copy_to_user`
- `get_user` / `put_user`
- `remap_pfn_range` / `mmap` 映射给用户
- 共享内存（本项目地毯 SHM 服务就是应用层间接方案）

### 19. Linux 启动完整流程（概念）

```
上电 → BootROM → Bootloader(U-Boot等)
  → 加载内核 + DTB
  → 内核初始化（驱动、根文件系统）
  → 第一个用户进程 init / systemd
  → 启动各服务（含本 network 进程）
  → main → HaierSdkNetwork::Init → 业务循环
```

本仓库只覆盖最后一环「应用启动」。完整板级启动要看：U-Boot、内核 `defconfig`、设备树、buildroot/`/etc/init.d`。
