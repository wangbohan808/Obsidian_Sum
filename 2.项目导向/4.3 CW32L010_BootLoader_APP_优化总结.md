## 1. 内存布局

```
Flash (64KB, 0x00000000 - 0x00010000)
┌──────────────────────────────────────┐
│ 0x00000000                           │
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │ BootLoader (4KB)
│  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │ 实际大小: ~1.9KB
│ 0x00000E00 ┌──────────────────────┐  │ ← ir_ota_addr (OTA触发标志)
│ 0x00000E08 │ app_update_flag      │  │ ← 升级完成标志
│ 0x00001000 ├──────────────────────┤  │
│            │                      │  │
│            │  APP (60KB)          │  │
│            │  实际大小: ~13KB     │  │
│            │                      │  │
│ 0x00010000 └──────────────────────┘  │
└──────────────────────────────────────┘

SRAM (4KB, 0x20000000 - 0x20001000)
┌──────────────────────────────────────┐
│ 0x20000000: DATA + BSS               │
│ 0x20000350: HEAP (0x200 bytes)       │
│ 0x20000550: STACK (0x200 bytes)      │
│ 0x20000E00: ARM_LIB_STACK (0x200 B)  │
│ 0x20001000: RAM 顶部                 │
└──────────────────────────────────────┘
```

**启动流程**:
```
上电复位 → 硬件从 0x0 加载 SP/PC → BootLoader 运行
  ├─ 检测 ir_ota_addr (0xE00)
  ├─ 第一次: 写标志 → 跳转 APP
  ├─ 正常启动: 检测到 app_update_flag → 跳转 APP
  └─ OTA模式: 从备份区(0x8800)拷贝固件到 APP 区(0x1000)
```

## 3. 每个修改的详细说明

### 修改 1: Flash 地址修正 (致命)

**问题**: CW32L010 是 Cortex-M0+，Flash 起始于 `0x00000000`，不是 STM32 的 `0x08000000`。
代码中硬编码了 STM32 风格的地址，所有 Flash 操作都会访问错误位置。

```c
// ❌ 修改前 (STM32 地址)
#define FLASH_APP_BASE_ADDR     0x08004000
FLASH_Read_half_apge(0x08008800+i*512, data);
app_flash_write(data, 0x08001000+i*512);

// ✅ 修改后 (CW32L010 地址)
#define FLASH_APP_BASE_ADDR     0x00001000
FLASH_Read_half_apge(0x00008800+i*512, data);
app_flash_write(data, 0x00001000+i*512);
```

**教训**: 不同 MCU 厂商的 Flash 基地址不同：
- STM32: `0x08000000`
- CW32L010: `0x00000000`
- 其他 Cortex-M: 查看芯片 Datasheet 的 Memory Map

---

### 修改 2: Flash 标志写入冲突 (致命)

**问题**: `app_update_flag_addr`(0xE08) 和 `ir_ota_addr`(0xE00) 在同一 Flash 页(512B)。
两个独立的 `app_flag_write()` 调用各自执行 `FLASH_ErasePage()`，第二个擦除会毁掉第一个写入的值。

**执行流程分析**:
```
1. app_flag_write(0x12345678, 0xE08)
   → FLASH_ErasePage(0xE08)  // 擦除 Page 0xE00~0xFFF
   → Write 0x12345678 @ 0xE08     ✅ 写入成功

2. app_flag_write1(0x66666666, 0xE00)
   → FLASH_ErasePage(0xE00)  // 💥 再次擦除 Page 0xE00~0xFFF!
   → 0xE08 的值 0x12345678 被擦毁 → 0xFFFFFFFF
   → Write 0x66666666 @ 0xE00     ✅

3. while(1) 循环中:
   → 读 0xE08 = 0xFFFFFFFF ≠ 0x12345678
   → receive_app_done 永远为 0
   → 无限循环，APP 永不启动！💀
```

**修复**: 同一页的标志在一次擦除周期内连续写入：

```c
// ✅ 修改后: 一次擦除 → 连续两次写入 → 一次锁定
FLASH_UnlockAllPages();
FLASH_ErasePage(ir_ota_addr);                       // 只擦一次
FLASH_WriteWords(app_update_flag_addr, (uint32_t[]){0x12345678}, 1);
FLASH_WriteWords(ir_ota_addr,         (uint32_t[]){0x66666666}, 1);
FLASH_LockAllPages();
```

**教训**: Flash 操作的最小单位是"页"(Page)，擦除会清除整页。同一页内的多次写入必须在一次擦除周期内完成。

---

### 修改 3: 时钟初始化 (重要)

**问题**: BootLoader 的 `main()` 调用的是 `SYSCTRL_Configuration()`(仅使能 FLASH/GPIOB 时钟)，
而不是 `RCC_Configuration()`(设置 HSI 48MHz)。

```c
// ✅ 修改后
int main(void)
{
    RCC_Configuration();                 // HSI = 48MHz
    __SYSCTRL_GPIOB_CLK_ENABLE();        // 按键检测用
    ...
}
```

---

### 修改 7: APP 启动代码 SP 加载 (致命)

**问题**: APP 链接在 `0x1000`，其向量表(含初始 SP)也在 `0x1000`。
但启动代码硬编码从 `0x0` (BootLoader 区域) 加载 SP。

```asm
; ❌ 修改前
Reset_Handler
    LDR     R1, =0x0          ; 从 BootLoader 区域读 SP!
    LDR     R0, [R1]
    MOV     SP, R0

; ✅ 修改后
Reset_Handler
    LDR     R1, =0x00001000   ; 从 APP 向量表(0x1000)读 SP
    LDR     R0, [R1]
    MOV     SP, R0
```

---

### 修改 8: APP 向量表偏移 VTOR (致命)

**问题**: Cortex-M 的 `SCB->VTOR` 寄存器告诉 CPU 中断向量表在哪里。
APP 在 `0x1000`，必须设置 `VTOR = 0x1000`，否则中断会跳到 BootLoader 的处理函数。

```c
// ✅ 修改后: system_cw32l010.c
#define USER_VECT_TAB_ADDRESS                          // 取消注释，启用 VTOR 配置

#if defined(USER_VECT_TAB_ADDRESS)
#define VECT_TAB_BASE_ADDRESS   0x00000000U
#define VECT_TAB_OFFSET         0x00001000U           // 改为 0x1000
#endif

void SystemInit(void)
{
    SCB->VTOR = VECT_TAB_BASE_ADDRESS | VECT_TAB_OFFSET;  // = 0x00001000
    ...
}
```

### 修改 10: csolution.yml 合并 target-set (致命)

**问题**: BootLoader 和 APP 在两个独立的 `target-set` 中。
pyOCD 每次只加载一个 project 的 hex，切换时会全片擦除再写入 → 两个固件互相覆盖。

```yaml
# ✅ 修改后: 单一 target-set 包含两个 images
target-types:
  - type: CW32L010F8
    device: CW32L010F8
    target-set:
      - set:
        images:
          - project-context: CW32L010_BootLoader.Debug   # 一起烧录!
          - project-context: CW32L010_APP.Debug
        debugger:
          name: CMSIS-DAP@pyOCD
          clock: 1000000
          protocol: swd
```

### 修改 12: launch.json 调试配置 (重要)

新增三种调试配置：

```json
// 1. BootLoader 调试 → 主调试目标为 BootLoader
//    同时加载 APP 符号文件 (add-symbol-file)
"name": "CMSIS_DAP@pyOCD (BootLoader)"

// 2. APP 调试 → 主调试目标为 APP
//    同时加载 BootLoader 符号文件
"name": "CMSIS_DAP@pyOCD (APP)"

// 3. 附加模式 → 连接到已运行的 GDB Server
//    不重新烧录
"name": "CMSIS_DAP@pyOCD (attach)"
```

每个 "launch" 类型配置的 GDB `initCommands` 中使用 `add-symbol-file` 加载另一个项目的符号。
这样无论调试哪个项目，都能查看两个项目的变量和调用栈。

**关键 initCommands 说明**:
```
"monitor reset halt"    → 复位芯片并暂停在第一条指令
"tbreak main"           → 在 main() 设置临时断点 (只触发一次)
"add-symbol-file ..."   → 加载辅助符号文件
```

## 附录: 常见问题排查

### Q: 烧录后 APP 不运行？
1. 检查标志位: `x/4x 0x00000E00` → 0xE08 应为 `0x12345678`
2. 确认 VTOR: `p/x *0xE000ED08` → 应为 `0x00001000`
3. 确认向量表: `x/8x 0x00001000` → 第一个 word 应在 SRAM 范围

### Q: Clean build 仍然用旧代码？
```powershell
Remove-Item -Recurse -Force tmp, out -ErrorAction SilentlyContinue
cbuild CW32L010_Firmware.csolution.yml --context-set --packs
```

### Q: pyOCD 报 "Board ID not recognized"？
这是正常警告，不影响功能。pyOCD 使用 CMSIS-Pack 中的 target 描述来操作芯片。

### Q: GDB 连接失败 (port 3333)？
确认 GDB Server 正在运行:
```powershell
netstat -an | findstr 3333
```
如果没有，先启动: `pyocd gdbserver --probe cmsisdap: --cbuild-run ...`
