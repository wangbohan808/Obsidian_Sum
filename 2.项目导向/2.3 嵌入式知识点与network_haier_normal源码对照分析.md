## 第 2 章：为什么中断处理函数中不能休眠

### 核心原因

1. **中断上下文没有进程调度信息** — 休眠需要保存/恢复进程状态，中断上下文不属于任何进程
2. **中断处理必须快速完成** — 休眠会导致中断响应延迟，影响系统实时性
3. **可能导致系统死锁** — 如果休眠时 CPU 空闲去运行其他进程，而那个进程需要当前中断完成才能继续，就形成了死锁
4. **内核调度器不能在中断上下文中运行** — `schedule()` 会主动检查是否在中断上下文

> 内核中有一句经典判断：`in_interrupt()` 返回真时绝不可以调用 `schedule()`。

### 本项目对照

本项目运行在用户空间，没有中断处理函数。但 HaierAdapter 处理设备状态回调（`HaierStatusCallback`）时需要注意：

```cpp
// haier_adapter.cpp:470 - 状态回调（在 OSDK 内部线程中执行）
uhsd_s32 HaierAdapter::HaierStatusCallback(uhsd_devHandle devHandle, UHSD_DEV_STATUS_E status, 
                                            uhsd_void *params, uhsd_void *userdata) {
    // ... 处理状态变化
    if (status == UHSD_DEV_STATUS_ROUTER_CONNECTED) {
        // OK：仅发起异步操作，不阻塞回调线程
        std::thread([] {
            LOGD("Router Connected, start to register ID");
            HAIER_ADPATER.RegisterDeviceId();
        }).detach();
    }
    return 0;
}
```

虽然这不是内核中断上下文，但回调通常运行在 SDK 内部工作线程中，如果在此回调中执行耗时操作（如 `sleep_for(10s)`），会阻塞 SDK 的其他处理。正确做法是**将耗时操作丢到独立线程**。

## 第 3 章：中断底半部（Bottom Half）- tasklet 与工作队列

### 概念解释

Linux 内核将中断处理分为两部分：
- **顶半部 (Top Half)**：执行紧急的硬件操作（清中断标志、读写寄存器），必须快速
- **底半部 (Bottom Half)**：处理耗时逻辑，稍后执行

底半部机制演进：
1. **tasklet** — 在软中断上下文中执行，不可休眠（基于 `HI_SOFTIRQ` / `TASKLET_SOFTIRQ`）
2. **工作队列 (Workqueue)** — 在进程上下文中执行，**可以休眠**（内核线程 `events/n`）

### 本项目对照

本项目是用户空间程序，没有使用内核 tasklet/workqueue。但项目的**异步/延迟执行模式**与底半部思想异曲同工：

```cpp
// haier_adapter.cpp:518 - 使用 detach 线程模拟"底半部"处理
std::thread([] {
    LOGD("Router Connected, start to register ID");
    HAIER_ADPATER.RegisterDeviceId();
}).detach();
```

项目中的异步执行对比：

| 内核机制 | 本项目对应 | 说明 |
|---------|-----------|------|
| tasklet | JTimer::setTimeout_ms | 延迟执行，不可阻塞 |
| workqueue | std::thread().detach() | 独立线程，可阻塞 |
| softirq | EventWorker + Subscriber | 事件驱动异步处理 |

```cpp
// timer.h:14 - JTimer 模拟"底半部"延迟执行
class JTimer {
    std::atomic<bool> active{true};
public:
    void setTimeout_ms(auto function, int delay) {
        active = true;
        std::thread t([=]() {
            if(!active.load()) return;
            std::this_thread::sleep_for(std::chrono::milliseconds(delay));
            if(!active.load()) return;
            function();
        });
        t.detach();
    }
};
```

## 第 4 章：DMA（Direct Memory Access）

### 概念解释

**DMA** 是一种允许硬件设备直接访问系统内存而无需 CPU 参与的技术。

**为什么用 DMA：**
1. **解放 CPU** — CPU 在 DMA 传输期间可以处理其他任务
2. **提高吞吐量** — 数据传输速度接近总线带宽
3. **降低功耗** — CPU 不需要频繁中断来处理数据搬运
4. **典型场景**：硬盘读写、网卡收发、音频采集播放、显示刷新

### 本项目对照

本项目是用户空间程序，**没有直接使用 DMA**。但项目涉及的大数据量处理（地图像素数据、路径数据）在整个系统中可能经过 DMA 传输：

```cpp
// map.cpp:196 - 处理大量地图像素数据（这些数据可能通过 DMA 从 SLAM 模块传来）
uint8_t *tmp_map_data = new (std::nothrow) uint8_t[1024 * 1024];
memcpy(tmp_map_data, slam_data_srv.response.data.data(), map_data_size);

// 对 1MB 地图数据进行像素格式转换
for (int y = 0; y < h / 2; y++) {
    for (int x = 0; x < w; x++) {
        tmpPix = map_data_ptr[x + y * w];
        // ... 像素转换逻辑
    }
}
```

## 第 5 章：IIC 读写错误排查

### 排查步骤

1. **检查硬件连接**：SDA/SCL 上拉电阻、电平匹配、接线是否正确
2. **确认设备地址**：7位/8位地址混淆、地址冲突
3. **检查时序**：用逻辑分析仪抓取波形，对比 datasheet 时序图
4. **软件排查**：
   - 确认从设备已准备好（有时需要延时重试）
   - 检查 ACK/NACK 状态
   - 使用 `i2cdetect -y <bus>` 检测设备是否存在

### 本项目对照

本项目是一个 Wi-Fi/BLE IoT 适配层，**没有直接 IIC 驱动代码**。但项目中存在类似的**重试-超时模式**，适用于 IIC 等外设通信：

```cpp
// haier_adapter.cpp:848 - 资源上传重试模式（与 IIC 重试逻辑类似）
int HaierAdapter::UploadResource(std::string rsc_name, uint8_t *data, uint32_t len) {
    std::lock_guard<std::mutex> lock(resource_upload_mutex_);
    int attempt = 0;
    int maxRetries = 3;
    int res = -1;
    while (attempt < maxRetries) {
        res = uhsd_dev_report_resource(gw_devHandle, ...);
        if (res == 0) {
            return res;  // 成功返回
        }
        attempt++;
        std::this_thread::sleep_for(std::chrono::seconds(1));  // 重试前等待
    }
    return res;  // 最终失败
}
```

这个模式是嵌入式外设通信（包括 IIC）的经典模板：**尝试→失败→等待→重试→最终放弃**。

如果 IIC 读写错误，在代码层面要检查：
- 地址和寄存器匹配
- 数据长度和缓冲区边界
- 超时时间是否合理

## 第 6 章：驱动模块 Panic 调试与 rundump/kkdump

### 概念解释

**Kernel Panic** 是 Linux 内核遇到致命错误时的行为，类似用户态的 Segfault。

**调试工具：**
- **rundump**：在系统运行时捕获内存快照（类似医生给正在运行的病人做检查）
- **kkdump**：内核崩溃时自动保存内存转储文件，重启后可分析

### 本项目对照

本项目提供了 **AddressSanitizer** 支持，可以在开发阶段检测内存错误（在嵌入式环境中类似 kkdump 的预防措施）：


## 第 7 章：工作队列中可以休眠吗？在什么上下文？

### 概念解释

| 机制 | 上下文 | 可以休眠？ | 说明 |
|------|--------|-----------|------|
| tasklet | 软中断上下文 | ❌ 不可休眠 | 运行在 `softirq` 中 |
| 工作队列 (workqueue) | 进程上下文 | ✅ 可以休眠 | 运行在内核线程 `kworker` 中 |

**工作队列在进程上下文**：
- 工作队列的函数运行在内核工作线程中（`kworker/x:x`）
- 这些线程是普通内核线程，有完整的进程上下文
- 因此可以调用 `msleep()`、`mutex_lock()` 等可能睡眠的函数

### 本项目对照

本项目使用 `std::thread` 代替工作队列。`std::thread` 运行在**用户空间进程上下文**，当然可以休眠：

```cpp
// path.cpp:14 - 线程中周期性执行，可以休眠
void Path::PathDataReport() {
    while (true) {
        int sleep_time_ms = 3000;
        PathFrameReport(false);
        std::this_thread::sleep_for(std::chrono::milliseconds(sleep_time_ms));
    }
}

// map.cpp:27 - 地图上报线程同样可以休眠
void HaierMap::MapDataReport() {
    while (true) {
        MapFrameReport();
        std::this_thread::sleep_for(std::chrono::milliseconds(1000 * 3));
    }
}
```

## 第 8 章：驱动可以直接访问用户空间内存吗？

### 概念解释

**不能直接访问**。原因：
1. 用户空间地址可能被换出到磁盘
2. 用户空间地址可能被重新映射
3. 安全隔离：内核不能信任用户提供的指针

**间接访问方法：**
- `copy_from_user()` / `copy_to_user()` — 最常用
- `get_user()` / `put_user()` — 单数据访问
- `access_ok()` — 检查地址范围
- `pin_user_pages()` — 锁定物理页帧

### 本项目对照

本项目是用户空间程序，不涉及内核内存访问。但项目中有一个相似的场景：**安全地复制字符串参数**：

```cpp
// haier_adapter.h 或 .cpp - 安全复制宏
#define SAFE_COPY(dest, src)              \
    strncpy(dest, src, sizeof(dest) - 1); \
    dest[sizeof(dest) - 1] = '\0'

// 使用示例
char all_file_path[256];
SAFE_COPY(info.app_id, appId.c_str());
SAFE_COPY(info.app_key, appKey.c_str());
SAFE_COPY(info.client_id, clientId.c_str());
```

**`SAFE_COPY` 与内核 `copy_from_user` 的类比**：
- 都确保目标缓冲区不会溢出
- 都是"不信任外部数据"的安全编程思路
- 都通过 `-1` 留出终止符位置

## 第 9 章：C++ RAII 机制与自动释放内存

### 概念解释

**RAII（Resource Acquisition Is Initialization）**：
- 资源在构造函数中获取，在析构函数中释放
- 利用栈对象的生命周期自动管理资源
- 异常安全：即使抛出异常，析构函数也会被调用

```cpp
// 典型 RAII 示例
{
    std::lock_guard<std::mutex> lock(mutex_);  // 构造函数中 lock()
    // ... 临界区 ...
}  // 析构函数中 unlock()，即使发生异常也会释放
```

### 本项目对照

RAII 在本项目中大量使用：

**1. `std::lock_guard` / `std::unique_lock` — 互斥锁的 RAII 包装**

```cpp
// haier_adapter.cpp:835
int HaierAdapter::HaierWriteHandle(const std::string &cmd, const std::string &cmd_value) {
    std::lock_guard<std::mutex> locker(write_mutex_);  // 自动加锁
    auto iter = cmd_obj_api_table_.find(cmd);
    if (iter != cmd_obj_api_table_.end()) {
        return iter->second(cmd_value);
    }
    return 0;
}  // locker 析构时自动解锁
```

```cpp
// map.cpp:153
void HaierMap::MapFrameReport(bool force) {
    std::unique_lock<std::mutex> lock(mutex_);  // RAII 上锁
    // ... 复杂的地图处理逻辑 ...
}  // 作用域结束自动解锁
```

**2. `std::unique_ptr` — 堆内存的 RAII 管理**

```cpp

auto app_id = std::make_unique<uhsd_char[]>(appId.size() + 1);
// 不需要手动 delete，unique_ptr 析构时自动释放

// app_id 自动释放
```

```cpp

if (!tmp_carpet_map_data) {
    LOGE("carpet raster alloc failed.");
    delete[] tmp_map_data;
    return;
}  // tmp_carpet_map_data 会在作用域结束时自动释放
```

**3. `std::shared_ptr` — 共享所有权 RAII**


## 第 10 章：动态管理内存的底层逻辑

### 概念解释

操作系统动态内存管理的底层逻辑：

1. **堆内存管理**：`malloc` → `brk()`/`sbrk()` 系统调用 → 内核管理进程堆
2. **伙伴系统 (Buddy System)** — 内核物理页管理（以 2^n 页为单位）
3. **SLAB 分配器** — 内核中针对小对象的缓存分配
4. **自由链表 (freelist)** — `malloc` 内部维护不同大小的空闲块链表
5. **内存碎片**：外部碎片（空闲块不连续） vs 内部碎片（分配大于需求）

### 本项目对照

**1. `new (std::nothrow)` — 不抛异常的动态分配**

```cpp
// map.cpp:196 - 大块内存分配
uint8_t *tmp_map_data = new (std::nothrow) uint8_t[1024 * 1024];
if (tmp_map_data == nullptr) {
    LOGE("%s Memory allocation failed.", __FUNCTION__);
    return;  // 优雅处理 OOM
}
```

嵌入式环境中不推荐抛异常（异常会增加二进制体积和运行时开销），`nothrow` 版本是嵌入式 C++ 的标配。

**2. 裸 `new[]` + `delete[]` — 手动管理**

```cpp
// map.cpp:196
uint8_t *tmp_map_data = new (std::nothrow) uint8_t[1024 * 1024];
// ... 使用 ...
delete[] tmp_map_data;  // 手动释放
```

在 `map.cpp` 中可以看到，既用了 `new[]`/`delete[]` 也用了 `unique_ptr`，说明项目正从手动管理向 RAII 迁移。

**3. 内存分配的实际调用链**

当代码执行 `new uint8_t[1024*1024]` 时，底层发生了什么：
```
new[] → operator new[] → malloc(1MB) → 
    brk() 系统调用 → 内核分配 1024 页物理内存 → 
    返回用户空间虚拟地址
```

## 第 11 章：多态与虚函数表

### 概念解释

**多态 (Polymorphism)**：
- 同一接口在不同对象上有不同实现
- C++ 通过虚函数实现运行期多态

**虚函数表 (vtable)**：
- 每个有虚函数的类都有一个 vtable（编译期生成）
- vtable 存储虚函数指针数组
- 每个对象有一个 `vptr` 指向所属类的 vtable
- 调用虚函数时：`obj->vptr[index](args)` — 间接跳转，比普通函数调用多一次寻址

### 本项目对照

项目中使用**虚函数 + 工厂方法**实现多态的房间属性帧编码：

```cpp

    virtual void SubDecode() = 0;                    // 纯虚函数
    virtual uint32_t SubFrameSize() = 0;             // 纯虚函数
    virtual void Serialize(const AutoAreaInfo &area_info) = 0;  // 纯虚函数

    // 非虚公共接口
    std::vector<uint8_t> Encode();
    int Decode();
    uint32_t FrameSize();
```

## 第 12 章：内存泄漏场景

### 典型场景

1. **malloc/new 后忘记 free/delete**
2. **异常路径中跳过释放代码**
3. **容器中的指针未清理**
4. **循环引用（shared_ptr 环）**
5. **回调闭包捕获了不再需要的对象**

### 本项目对照

**场景 1：异步回调中的潜在泄漏**

```cpp
// haier_adapter.cpp:51-102 - 异步文件上传
bool uhsd_push_file_to_oss_blocking(...) {
    auto *cb_param_ptr = new CallbackWrapper(promise_ptr);  // 堆分配
    int call_result = uhsd_push_file_to_oss(..., cb, cb_param_ptr);
    
    if (call_result != 0) {
        delete cb_param_ptr;  // 失败时主动释放
        throw std::runtime_error("...");
    }
    // 正常路径：cb_param_ptr 在回调中通过 delete wrapper_ptr 释放
    
    if (result_future.wait_for(timeout) == std::future_status::ready) {
        return true;  // 回调已执行，cb_param_ptr 已被删除
    } else {
        // 超时！但回调可能之后仍然执行
        // 风险：如果回调在超时后执行，会访问已被析构的 promise
        return false;
    }
}
```

**这里的潜在问题**：
- 超时返回 `false` 后，如果回调之后才触发，`callback` 中的 `set_value` 会设置在已析构的 `promise` 上
- 文档中已记录此问题（见 `dev_log/` 中的分析）

**场景 2：裸指针的异常安全**

```cpp
// map.cpp:196-218
uint8_t *tmp_map_data = new (std::nothrow) uint8_t[1024 * 1024];
if (tmp_map_data == nullptr) return;

// ... 中间代码可能抛异常 ...

// 只有正常路径才会执行 delete[]

```

如果中间的代码抛出异常，`delete[]` 不会执行。更好的做法是用 `unique_ptr`。

## 第 14 章：优先级反转

### 概念解释

**优先级反转 (Priority Inversion)**：高优先级任务被低优先级任务阻塞，而中优先级任务抢占低优先级任务，导致高优先级任务无限期等待。

**典型场景**：
1. 低优先级任务持有锁 L
2. 高优先级任务请求锁 L，被阻塞（让出 CPU）
3. 中优先级任务运行（不需要锁 L），抢占 CPU
4. 低优先级任务无法运行 → 无法释放锁 L
5. 高优先级任务无限等待

**解决方案**：
1. **优先级继承 (Priority Inheritance)**：低优先级任务临时继承高优先级任务的优先级
2. **优先级天花板 (Priority Ceiling)**：锁的优先级设为所有可能请求者的最高优先级
3. **禁止抢占 (Disable Preemption)**：持有锁时禁止调度

### 本项目对照

项目中虽然没有内核优先级反转问题，但**用户空间线程同样存在类似的优先级问题**：

```cpp
// dev_status.cpp:173 - 使用 mutex 保护共享状态

    std::lock_guard<std::mutex> locker(status_mtx_);  // 持锁
    // ... 长时间的状态读取操作（调用 CallServer、解析 JSON）...
}

// 另一个线程同时请求同一把锁
void DevStatus::StatusForceReport(const StdStringMsg &dev_status) {
    // 如果在这里也需要 status_mtx_，就会被阻塞
}
```

**预防措施在本项目中的体现：**
1. **尽量缩小临界区** — 只保护必要的共享数据
2. **使用独立的锁** — 不同资源用不同锁，减少冲突


## 第 18 章：Linux 启动完整流程

### 嵌入式 Linux 启动流程

```
Boot ROM → Bootloader(uboot) → Kernel → init进程 → 系统服务 → 用户应用程序
```

**1. Boot ROM（芯片固化的启动代码）**
- 上电后 CPU 从固定地址（如 0x00000000）开始执行
- 初始化基本硬件（时钟、SDRAM 控制器）
- 加载 Bootloader 到 RAM 并跳转

**2. Bootloader（uboot）**
- 进一步初始化硬件（DDR、串口、NAND Flash）
- 从存储介质加载内核和设备树（DTB）
- 设置内核启动参数（ATAG / DTB）
- 跳转到内核入口

**3. Linux Kernel**
- `start_kernel()` → `setup_arch()` → `trap_init()` → `mm_init()` → `init_IRQ()`
- 初始化调度器 → 创建 `init` 进程（PID=1）

**4. init 进程**
- **Busybox init**：读取 `/etc/inittab`，启动 shell
- **systemd**：并行启动服务（复杂嵌入式系统用）

**5. 系统服务启动**
- 网络服务（DHCP、Wi-Fi 连接）
- 各业务服务（SLAM、导航、底盘控制等）
- IoT 守护进程（本项目）

### 概念解释

**中断上下文 (Interrupt Context)**：
- CPU 执行中断服务程序 (ISR) 时处于中断上下文
- 特点是：异步发生、不可阻塞、不可睡眠
- 不归属任何进程，没有 `current` 指针
- 中断上下文中不能调用可能导致睡眠的函数（如 `copy_from_user`、`kmalloc(GFP_KERNEL)`）

**进程上下文 (Process Context)**：
- 用户态程序通过系统调用进入内核时处于进程上下文
- 可以睡眠、可以被抢占
- 有 `current` 指针指向当前进程
- 内核线程和普通进程的系统调用都在进程上下文中执行

### 本项目对照

本项目是一个**用户空间守护进程**，所有代码都运行在**进程上下文**中，不涉及中断上下文。

```cpp
// main.cpp - 主进程上下文
int main(int argc, char *argv[]) {
    LOGD("TUYA SDK Demo start run ... ");
    if (HAIER_IOT::HAIER_SDK_NETWORK.Init() != 0) {
        LOGE("TuyaSdkNetwork Init failed.");
    }
    while (1) {
        std::this_thread::sleep_for(std::chrono::milliseconds(1000 * 10));
    }
    return 0;
}
```

关键点：
- `main()` 运行在进程上下文，可以自由调用 `sleep_for`
- `while(1)` 让进程常驻后台，这是 IoT 守护进程的典型模式
- `sleep_for(10s)` 周期性唤醒检查任务

### 补充说明

本项目虽然没有中断上下文，但调用的 Haier OSDK 库内部的网络 I/O 底层可能涉及硬中断和软中断。用户空间程序通过 socket 等接口与内核交互时，数据从网卡硬件→内核驱动中断处理→软中断→用户空间进程，经历了完整的中断→进程上下文切换过程。
