# 音视频底层原理：从像素到 RTMP

> [!info] 一句话核心
> 直播链路 = 一条典型的嵌入式音视频管线，只是换了个壳。
> **压缩的全部成本花在"运动估计"上，编码器的真实瓶颈是 DDR 带宽而不是编码单元。**
> 记住三个数量级：1080p60 未压缩 237 MB/s → 编码后 1 MB/s → 压缩比约 240:1。

> 背景：由 [[02_直播推流术语与链路]]（《异人之下》直播方案）延伸，目的是把"调设置"下沉到"懂原理"。
> 面向岗位：Linux 嵌入式音视频（推理部署邻近方向）。

---

## 零、入门坡度：从已有的经验接上去

> [!note] 读法提示
> 第一到第八节是完整原理，**不适合从头顺读**。先跑通本节的最小实验，带着疑问再回头查。
> 音视频不是一门新学问，是"采集 + 显示 + 传输"三件事换了一组外设和数据格式。

### 0.1 已有经验的映射

| 已经做过的事 | 音视频里的同一个东西 | 差别 |
| --- | --- | --- |
| 集尘桶：读传感器、写驱动、配 DMA（C / MCU） | 读摄像头帧（V4L2） | 传感器一次给 2 字节，视频一帧给 3 MB |
| 串口接收的环形缓冲区（生产者-消费者） | V4L2 的 buffer 队列（`QBUF` / `DQBUF`） | **同一个模型**，只是帧排成队列 |
| MCU 里 DMA 搬运，CPU 不参与 | DMA-BUF 零拷贝 | 概念相同，粒度从 1 字节变成一整帧 |
| 治具 UI 定时刷新数据（Python） | 60fps 画面刷新 | 1 Hz 刷一个数字 vs 60 Hz 刷一张图 |
| IoT 进程打包 + socket 上传云端（C++） | RTMP 推流 | **都是按协议把数据发到服务器** |
| 自定义协议包（头 + 数据 + 校验） | FLV tag（类型 + 长度 + 时间戳） | 结构同构 |
| 定时器里读最新一次采样值 | 按 60 Hz 取最新一帧 | 帧率就是"采样率" |

### 0.2 真正的缺口只有三个

| # | 缺口 | 一句话说清 |
| --- | --- | --- |
| 1 | **帧带时间戳，不是一张图片** | 每帧有 PTS，播放端按时间戳决定何时显示。**所有卡顿/音画不同步/延迟问题，根都是时间戳没对上** |
| 2 | **压缩有损，且损失取决于"变化量"** | H.264 传的是"与上一帧的差值"。静止几乎不占码率，打斗瞬间爆码率。**码率是给"变化"花的** |
| 3 | **数量级差两个零** | IoT 数据 KB/s，音视频 186 MB/s。**这个规模下瓶颈是内存带宽，不是 CPU 算力**——优化目标从"省指令周期"变成"省内存搬运" |

> 其余所有概念都是这三条的推论。

### 0.3 第一个实验（不碰直播，先抓一帧）

ROCK 5C 插一个普通 UVC 摄像头（数十元即可，不需要采集卡）：

```bash
v4l2-ctl --list-devices                      # 系统认出了什么
v4l2-ctl -d /dev/video0 --list-formats-ext   # 支持哪些格式与帧率
ffmpeg -f v4l2 -i /dev/video0 -t 10 test.mp4 # 录 10 秒
```

**这 10 秒已走完直播链路的全部环节**（采集 → 压缩 → 封装），只是终点从"推流"换成"写文件"。

跑通后必然产生三个疑问，此时再讲原理才进得去：
1. 为什么同一分辨率有好几种格式（YUY2 / NV12 / MJPG）？
2. 为什么文件比原始数据小那么多（压缩比）？
3. 为什么换个摄像头就要改参数（格式协商）？

### 0.4 四步推进（每步都能独立跑通）

| 步 | 目标 | 学到什么 | 量级 |
| --- | --- | --- | --- |
| 1 | UVC 摄像头 → 录成 MP4 | V4L2 基本操作、格式协商 | 1 个下午 |
| 2 | 同上，改为推 RTMP 到 B 站 | 编码器、封装、推流协议、延迟构成 | 1 个周末 |
| 3 | 换成采集卡 + HDMI | UVC 兼容性、YUY2→NV12、DMA-BUF | 1 个周末 |
| 4 | 加音频、调音画同步 | ALSA、PTS、时钟漂移 | 1–2 周 |

第 2 步做完即可开播；第 3、4 步是打磨。

## 一、像素格式：内存排布决定带宽

| 格式 | 内存排布 | 1080p 一帧 | 典型用途 |
| --- | --- | --- | --- |
| RGB24 | 交错 `R G B` | 6.2 MB | 游戏渲染、截图 |
| YUY2 / YUYV | 打包，每 2 像素 4 字节 `Y0 U0 Y1 V0` | 4.15 MB | HDMI 采集卡（HDMI 本身即 4:2:2，直通零转换） |
| NV12 | 半平面：Y 全平面 + UV 交错半平面 | 3.1 MB | **硬件编码器首选输入** |
| I420 / YUV420P | 三平面 Y / U / V 各自连续 | 3.1 MB | x264、ffmpeg 默认 |

### 色度采样的由来

人眼视杆细胞（亮度）约 1 亿，视锥细胞（色度）约 600 万且集中于中央凹 → **色度可大幅降采样而不被察觉**。

| 采样 | 色度共享范围 | bit/px |
| --- | --- | --- |
| 4:4:4 | 每像素独立 | 24 |
| 4:2:2 | 每 2 列共享 | 16 |
| 4:2:0 | 每 2×2 共享 | 12 |

> [!tip] NV12 为何是硬编首选
> 编码器按 16×16 宏块工作。NV12 中一个宏块的 UV 连续存放，DMA 一次突发即可取完；
> I420 需跳三个平面，三次地址跳转，缓存命中率更差。**这是接 RK MPP / 海思 VENC 的第一个格式约束。**

### USB 带宽的物理下限

1080p60 YUY2 = 249 MB/s；USB 2.0 实际有效约 35 MB/s，**差 7 倍** → 廉价卡只能给 MJPEG。这是物理限制，不是厂商偷工。

## 二、色彩空间与范围

### 亮度系数

| 标准 | 公式 | 用途 |
| --- | --- | --- |
| BT.601 | Y = 0.299R + 0.587G + 0.114B | 标清 |
| BT.709 | Y = 0.2126R + 0.7152G + 0.0722B | 高清 |

矩阵用错 → 饱和度偏移、肤色偏向，且不报错。

### 范围（Range）

| | Y | Cb/Cr | 场景 |
| --- | --- | --- | --- |
| Limited（部分） | 16–235 | 16–240 | 视频标准（源于模拟信号需保护带） |
| Full（全） | 0–255 | 0–255 | 计算机图形、截图 |

Limited 当 Full 显示 → 对比度被压 → **灰蒙蒙**；Full 当 Limited → 过曝死黑。

> [!warning] 这个 flag 会在四个环节丢失
> ```
> 显卡输出 → HDMI AVI InfoFrame → 采集卡是否透传 → 编码器 VUI(video_full_range_flag) → 平台解码
> ```
> Linux 侧对应 `V4L2_PIX_FMT_*` 的 `quantization` 字段（`V4L2_QUANTIZATION_LIM_RANGE` / `FULL_RANGE`）。
> **很多采集卡驱动根本不透传此字段**，故同一卡在不同软件颜色不同。

## 三、传输层：HDMI 与 UVC

### HDMI

- **TMDS**：3 对数据 + 1 对时钟，8b/10b 编码
- 8b/10b 的目的是**直流平衡**（供接收端交流耦合 + 时钟恢复），代价是 20% 带宽税
- 1080p60 需 4.455 Gbps（3 × 1.485G），HDMI 2.0 的 18 Gbps 远够 → **带宽不是瓶颈，编码才是**

| 机制 | 作用 | 失败现象 |
| --- | --- | --- |
| EDID | I²C 上的能力表，声明支持的格式 | 上报错 → 无信号或分辨率被锁 |
| HDCP | 内容加密 | 源端要求而卡不支持 → 黑屏 |
| AVI InfoFrame | 每帧携带色彩空间/范围/扫描方式 | 偏色、发灰 |

> [!important] 认知前提
> **采集卡在协议上是"一台显示器"（sink），不是"一台录制设备"。**
> 它必须完整实现 sink 行为：读 EDID、应答 HDCP、解析 InfoFrame。便宜卡兼容性差的根源就是省了这些。

### UVC

USB Video Class：标准描述符 + 免驱。Linux 下由 `uvcvideo` 驱动创建 `/dev/videoN`。

**关键映射：在 RK3588 上插 UVC 摄像头，和在 Windows 上插采集卡，走的是同一套 V4L2 代码路径。**

## 四、压缩：H.264 六步

三种冗余：**空间**（相邻像素相似）、**时间**（相邻帧相似）、**心理视觉**（人眼不敏感）。

| # | 步骤 | 做什么 | 要点 |
| --- | --- | --- | --- |
| 1 | 分块 | 16×16 宏块 → 变换块 | H.265 改为 CTU 四叉树 |
| 2 | **预测** | 帧内：用左/上已解码像素预测（9 模式）<br>帧间：运动估计找参考块，只传运动矢量 + 残差 | **决定压缩率上限** |
| 3 | 变换 | 整数 DCT 近似，能量集中到低频 | 整数运算避免误差累积 |
| 4 | 量化 | 除以量化步长，丢高频 | **唯一有损环节**，QP 控制 |
| 5 | 熵编码 | CAVLC / CABAC | 无损；CABAC 省 10–15% |
| 6 | 环路滤波 | Deblocking 平滑块边界 | 不做则低码率全方块 |

> [!important] 核心洞察
> **码率是给"变化"花的，不是给"画面"花的。**
> 格斗游戏/体育赛事最难压：快速位移 + 特效 + 镜头晃动 → 运动估计找不到好匹配 → 残差巨大。
> 这就是"同样 8Mbps，站着不动清晰、打起来糊成一片"的物理原因。

### 帧类型与 GOP

| 帧型 | 依赖 | 体积 | 延迟 |
| --- | --- | --- | --- |
| I | 自身独立 | 大（P 的 10–20×） | 0 |
| P | 前向参考 | 中 | 0 |
| B | **前后双向** | 小 | **+1~3 帧**（须等后续帧） |

- **IDR**：特殊 I 帧，清空 DPB（解码图像缓冲），是唯一随机接入点。**新观众必须等下一个 IDR 才有画面** → 平台强制关键帧间隔 ≤2 s 的原因。
- **直播禁用 B 帧**（`bframes=0`）：重排序引入延迟，格斗游戏不可接受。
- MPP 对应参数：`rc_mode`、`gop_len`、`bps`。

## 五、码率控制与硬件编码器

| 模式 | 逻辑 | 场景 |
| --- | --- | --- |
| CBR | 恒速，VBV 漏桶约束突发 | **直播**（平台按恒速收） |
| VBR | 恒质量，码率随复杂度浮动 | 点播、录制 |
| ABR | 目标平均码率 | 折中 |
| CRF | x264 特有，按视觉质量分配 | 本地存档 |

VBV 是"漏桶"：桶容量决定允许的瞬时突发。直播常设 1–2 s。**桶小 → 质量剧烈波动；桶大 → 突发撑爆上行**——这就是码率拉满反而更卡的原因。

> [!important] 嵌入式评估铁律
> 硬件编码器是固定功能 ASIC，不占通用算力，但**不是免费**：要读 NV12 帧、写码流。
> 1080p60 NV12 读一遍即 186 MB/s，运动估计要反复读参考帧 → **实际 DDR 带宽需求可达标称的 2–3 倍**。
>
> **编码器的瓶颈几乎从不是"编码单元算力"，而是 DDR 带宽预算。**
> RK3588 上多路编码掉帧，八成是 DDR 被抢，不是 VPU 不够。看参数表没用，要算内存带宽。

## 六、协议与延迟

| 协议 | 传输层 | 延迟 | 抗丢包 | 场景 |
| --- | --- | --- | --- | --- |
| RTMP | TCP 1935 | 2–5 s | 差（队头阻塞） | 主流推流 |
| SRT | UDP + ARQ | 可配 0.1–3 s | **强** | 弱网、远距离 |
| WebRTC | UDP / SRTP | **< 500 ms** | 中 | 连麦、低延迟互动 |
| HLS / LL-HLS | HTTP 切片 | 6–30 s / 2–5 s | 强 | 大规模分发 |

### RTMP 结构

1. **握手**：C0/C1/C2 + S0/S1/S2
2. **分块（Chunk）**：默认 128 B，可协商至 4096（OBS 如此）。大块降头部开销、升单包延迟
3. **命令**：AMF0 序列化，`connect` → `createStream` → `publish`
4. **封装**：FLV tag（audio / video / script）

> RTMP 走 TCP → 丢包重传会阻塞后续全部数据（**队头阻塞**），这是它延迟下限 2 s 的根因。
> SRT 用 UDP + 选择性重传才把延迟压进 0.5 s，代价是自行处理乱序。

## 七、音频与 A/V 同步

**音频与视频是两条独立时钟**，晶振都不准。

算一笔账：48 kHz 晶振误差 ±60 ppm（正常水平）→ 实际 47,997 Hz → **一小时累计漂移 ≈ 10,368 采样 ≈ 216 ms**。两小时直播口型能差出小半秒。

**解法：audio master clock。** 以音频为基准，视频帧按 PTS 对齐，慢了丢帧、快了重复帧。OBS 的"同步偏移"即手动补偿。

> 与嵌入式对应：`PTS` 打戳 → 选主时钟 → 从时钟追主时钟。
> GStreamer 的 `avsync` 属性、ffmpeg 的 `-async` 参数，背后是同一套。

## 八、映射到 Linux 嵌入式栈

| 直播概念 | 对应技术 | 关键 API / 结构 |
| --- | --- | --- |
| 采集卡 | UVC → **V4L2** | `VIDIOC_S_FMT` / `REQBUFS` / `QBUF` / `DQBUF` |
| 格式协商 | fourcc（`YUYV` / `NV12`） | `v4l2_format.fmt.pix.pixelformat` |
| 色彩范围 | quantization | `V4L2_QUANTIZATION_LIM_RANGE` |
| 零拷贝 | **DMA-BUF** | `VIDIOC_EXPBUF` → `drmPrimeFDToHandle` |
| 环出显示 | **DRM/KMS** | plane / crtc / connector |
| 硬件编码 | RK **MPP** / 海思 **VENC** / VAAPI | `mpp_enc`、`MPI_VENC_SendFrame` |
| 音频采集 | **ALSA** | `snd_pcm_readi` |
| 封装 | ffmpeg `libavformat` | `avformat_write_header` |
| 管线编排 | **GStreamer** | `v4l2src ! mpph264enc ! flvmux ! rtmpsink` |

### 一条可跑的 RK3588 管线

```bash
gst-launch-1.0 v4l2src device=/dev/video0 ! \
  video/x-raw,format=NV12,width=1920,height=1080,framerate=60/1 ! \
  mpph264enc rc-mode=cbr bps=8000000 gop=120 ! \
  h264parse ! flvmux ! \
  rtmpsink location="rtmp://..."
```

**这与 OBS 所做完全相同**，只是 OBS 把每一环做成了 GUI。
