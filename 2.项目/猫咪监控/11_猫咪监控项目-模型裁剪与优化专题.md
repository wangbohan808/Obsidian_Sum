# 11 猫咪监控项目：模型裁剪与优化专题

> 目标：把"猫检测 + 行为判定"模型做到 **小、快、准**，这是简历中"AI 模型的裁剪优化"的支撑材料。
> 覆盖：模型小型化选型 → 量化（INT8）→ 剪枝/稀疏 → 蒸馏 → 输入侧优化 → NPU 运行时调优 → 评估闭环。

---

## 1. 为什么需要优化（先量化收益）

RK3588 NPU 标称 6 TOPS（INT8），但：

- NPU 带宽与内存有限，模型越大越容易受 L2 缓存/带宽限制；
- 端侧设备长期运行，功耗与发热直接影响稳定性；
- 猫监控是 24 小时任务，推理越快，CPU/内存留给系统与录制越充裕。

**优化目标（本项目）**：

| 指标 | 优化前（YOLOv8s fp） | 优化后目标（YOLOv8n int8 + 输入裁剪） |
| --- | --- | --- |
| 模型体积 | ~22 MB | ~6 MB（INT8 后 YOLOv8n 权重约 6MB） |
| 单帧推理 | 未量化 CPU 无法实时 | 10~30 ms（640 输入）/ 5~15 ms（416 输入） |
| NPU 内存占用 | — | < 300 MB |
| 精度 | — | mAP@50 ≥ 0.9（单类猫，测试集） |

## 2. 优化链路总览

```text
基线模型（YOLOv8s/v8n，COCO 80 类）
   │ ① 任务裁剪：改为单类 cat（类别数 80→1，输出张量 84→6）
   │ ② 模型小型化：换 YOLOv8n；可选蒸馏自 YOLOv8m
   │ ③ 输入侧：分辨率 640→416/320；帧率 10fps；ROI 裁剪后只推理小区域
   │ ④ 量化：RKNN INT8 PTQ（校准集贴近场景）→ 必要时混合精度/QAT
   │ ⑤ 剪枝/稀疏（进阶）：channel pruning / autosparsity（注意平台限制）
   │ ⑥ 运行时：NPU 多核、零拷贝、RGA 缩放、流水线并行
   ▼
验证：精度（mAP/混淆矩阵）+ 延迟 + 内存 + 功耗
```

## 3. 模型小型化与任务裁剪

### 3.1 选型对比（RK3588 上 INT8 实测量级）

| 模型 | 参数 | INT8 体积 | 640 输入推理（NPU） | 适用性 |
| --- | --- | --- | --- | --- |
| YOLOv8n | 3.2M | ~6 MB | 15~30 ms | ✅ 首选 |
| YOLOv8s | 11M | ~22 MB | 30~60 ms | 备用（精度更稳） |
| YOLOv8n-pose | 3.3M | ~7 MB | 20~35 ms | 需要头部关键点时 |
| MobileNetV3-Small | 2.5M | ~5 MB | 5~15 ms | 分类器 |
| YOLOv8n-cls | 1.8M | ~3.5 MB | 5~10 ms | 行为分类兜底 |

> 实测数值随 RKNN 版本与驱动版本浮动，文档 05 的 benchmark 与 rknn_model_zoo 的耗时数据可作参考。

### 3.2 任务裁剪（单类化）带来的收益

YOLOv8 输出为 `4 + nc + 1` 通道（nc=类别数）。80 类 → 1 类：

- 输出张量从 `84×8400` 变 `6×8400`，后处理与带宽显著下降；
- 训练数据只需猫框标注；
- 推理端跳过"非猫类"过滤，逻辑更简单。

做法：文档 10 第 4 节用 `cat.yaml`（单类）微调即可。

## 4. 量化（RKNN INT8）——本项目收益最大的优化

### 4.1 原理一句话

把 fp32 权重/激活从 32 位降到 8 位整数（或 4 位），配合 per-channel 缩放因子，模型体积缩小约 4 倍，NPU 吞吐提升数倍，代价是精度损失（通常 <1~3% mAP）。

### 4.2 RKNN-Toolkit2 量化关键参数

```python
rknn.config(
    target_platform='rk3588',
    mean_values=[[0, 0, 0]],
    std_values=[[255, 255, 255]],
    quantized_dtype='asymmetric_quantized-8',  # 非对称量化，对激活分布更友好
    quantized_algorithm='mmse',                # 'normal' | 'mmse'（更慢但更准）
    optimization_level=3,                      # 0-3，值越高算子融合越多
)
```

### 4.3 校准集（决定量化精度）

- 500 张以内足够，但必须**来自真实部署场景**；
- 覆盖：白天/夜晚、顺光/逆光、猫在/不在、进食/饮水/停留；
- 建议从采集数据中按比例抽样，写进 `calib_dataset.txt`。

### 4.4 量化失败时的三板斧

1. **换量化算法**：`normal` → `mmse`；
2. **混合量化**：把敏感算子（如最后的检测头卷积）保持 fp16：

```python
from rknn.api import RKNN
# 在 config 中用 quantized_dtype 指定局部精度（以当前 RKNN-Toolkit2 2.3.x 文档为准）

# 或通过 custom op / 算子替换 API 指定
```

3. **量化感知训练（QAT）**：在 PyTorch 里加 `torch.ao.quantization` 伪量化节点训练 20~50 epoch，再导出 ONNX 转换，INT8 精度最稳（成本最高）。

### 4.5 验证流程（必须做）

# 2) 板端跑验证集：分别加载 fp16 与 int8 .rknn，对比 mAP

## 5. 剪枝与稀疏（进阶，简历亮点）

### 5.1 通道剪枝（Channel Pruning）

思路：训练后按 BN 层 gamma 或 Taylor 重要性裁剪冗余通道，再微调恢复精度。工具：

- PyTorch 官方：`torch.nn.utils.prune`（结构化裁剪需自写）；
- OpenVINO NNCF：`nncf.compress_weights` / filter pruning（对 PyTorch 模型友好，导出的 ONNX 可继续走 RKNN）；
- 手工方案：裁剪 YOLO 最后一层大通道数的 C2f 模块（需改 yaml 结构，重新训练）。

本项目建议：

```bash
# 用 NNCF 对 YOLOv8n 做 20~30% 通道剪枝（保留 cat 检测精度），导出 ONNX 再转 RKNN
conda activate yolo
pip install nncf
python3 ai/prune_nncf.py --model cat_yolo/run1/weights/best.pt \
    --data cat.yaml --sparsity 0.25 --epochs 30
# 产出 pruned.onnx → 按文档 10 §5.1 转 RKNN
```

收益预期：体积再降 20~30%，推理提速 10~20%；代价是训练时间增加。

### 5.2 结构化稀疏（AutoSparsity，Rockchip 官方工具）

本机已有 `rknn-toolkit2-2.3.2/autosparsity/`（v1.0 wheel，训练时做 2:4 结构化稀疏，推理端用稀疏内核加速）：

```bash

pip install packages/autosparsity-1.0-cp311-cp311-linux_x86_64.whl
```

```python

# 在训练循环前插入：

```

> **重要限制（已核实 README）**：AutoSparsity 的**稀疏推理目前仅支持 RK3576 平台**。RK3588 上可以训练得到稀疏模型（体积/理论计算量下降），但推理加速依赖后续 RKNN 工具链支持。本项目把它列为"方法论展示 + 未来适配"，主优化仍以 INT8 量化为准。

### 5.3 知识蒸馏（可选）

大模型（教师）教小模型（学生）：

- 教师：YOLOv8m 微调后的 cat 检测器；
- 学生：YOLOv8n；
- 损失：`L = α·L_task + (1-α)·L_kl(logits_student, logits_teacher)`；

收益：小模型精度向大模型靠拢，典型 mAP +1~3%。

## 6. 输入侧优化（性价比最高的"免费"优化）

| 手段 | 说明 | 收益 |
| --- | --- | --- |
| 降低输入分辨率 | 640→416（甚至 320） | 推理延迟约降 40~60%；猫是大目标，320 通常够 |
| 降低推理帧率 | 10fps 抽帧（录制仍 15fps） | NPU 负载减半 |
| ROI 预裁剪 | 只在碗区/水区附近小窗口跑检测（先用运动框住区域） | 输入变小 + 减少误检 |
| YUV 直通 | 用 NV12 而非 RGB 输入（若模型支持） | 省去色彩转换与拷贝 |
| 减少预处理 | 用 RGA 硬件缩放替代 cv2.resize（CPU） | CPU 释放，可并发 |
| 固定分辨率 | 摄像头固定 720p，AI 固定 416 | 避免分辨率抖动重初始化 |

## 7. NPU 运行时调优

### 7.1 RKNN-Lite2 运行时参数

```python
from rknnlite.api import RKNNLite

eng = RKNNLite()
eng.load_rknn('cat_det_int8.rknn')
eng.init_runtime(
    core_mask=RKNNLite.NPU_CORE_AUTO,   # 自动用满 3 核；小模型也可绑定 NPU_CORE_0 留核给其他任务
    # async_inference=True,             # 异步推理（API 版本支持时），与采集并行
)
```

### 7.2 零拷贝（zero-copy）

采集帧 → RGA 缩放 → DMABUF → NPU 推理 → 输出，全程避免 memcpy：

- C++ RKNN Runtime 支持 `rknn_create_mem` / `rknn_set_io_mem` 绑定 dmabuf fd；
- GStreamer `v4l2src` + `dmabuf` caps + `appsink` 可拿到 dmabuf，再交给 RKNN；
- Python 原型阶段先不追求零拷贝，正式版（简历加分）实现 C++ 版。

### 7.3 流水线并行（三线程模型）

```text
线程1：采集（V4L2/RGA）→ 放入帧队列 A
线程2：推理（NPU）← 从 A 取帧 → 结果队列 B
线程3：状态机+录制 ← 从 B 取结果（不阻塞采集/推理）
```

Python 用 `queue.Queue(maxsize=2)` 实现，避免 GIL 长时间占用的关键是让 NPU 调用释放 GIL（rknnlite 的 `inference` 内部会释放）。

### 7.4 频率与功耗

## 9. 常见问题

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| INT8 后猫检测不到 | 校准集与场景不符 / 阈值问题 | 校准集加入夜晚与侧光帧；mAP 评估后调 conf 阈值 |
| 剪枝后精度暴跌 | 剪枝比例过大 / 未微调 | 20% 起步，剪后 30~50 epoch 微调 |
| `autosparsity` 转换报错 | 平台不支持稀疏推理 | 确认 README 限制（仅 RK3576）；RK3588 只做训练侧 |
| 推理延迟波动大 | NPU 频率升降 / 内存抖动 | 固定频率、降分辨率、关掉无关进程 |
| 量化后输出 NaN | 极端激活值 | 校准集加最大对比度帧；改用 normal 算法 |
