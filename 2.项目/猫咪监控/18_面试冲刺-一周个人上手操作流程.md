# 18 面试冲刺：一周「个人上手」操作流程

> 面向岗位：瑞莎 Radxa · 初级 Linux BSP / 多媒体驱动工程师（深圳，10–15K）
> 前置现状（已确认）：硬件 ROCK 5C + USB 摄像头 + WiFi + 构建机/虚拟机环境全部就绪；
> 关键事实：此前 `make test/sim/deb`、内核编译、Arch 镜像等均为 **AI 代跑，你本人未上手**。

---

## 0. 先立一条原则（比任何操作都重要）

面试官要的是「**你** 上手过板子和 SDK」，不是「你有一个 AI 跑通的仓库」。
所以本周一切操作由 **你亲手敲命令、亲手看输出**；AI 只提供命令清单和环境，不替你跑。
凡是你亲手跑懂的一步，就能在面试里讲；凡是没跑过的，一律说「了解概念、计划入职后深入」，绝不说「我做过」。

## 2. 阶段 0：板子上电与 Bring-up（半天）

目标：亲手完成「烧录 → 启动 → 进系统 → 看日志」，这是 JD 职责 3「系统启动流程、板级调试、Hardware Bring-up」的最直接证据。

### 2.1 确认启动介质与镜像

二选一（你手上环境为准）：

- **优先 A：官方 RadxaOS**（干净、有 `rsetup`、社区资料全，最适合第一次亲手跑）。
- **次选 B：AI 已构建的 Arch 镜像** `arch/output/rock5c-arch.img`（能证明「我理解过启动链」，但因为不是你编的，只能作为启动介质，别编故事）。

### 2.2 烧录到 SD 卡（亲手敲，注意别烧错盘）

```bash
lsblk                                  # 先确认 SD 卡设备名（/dev/sdb 之类，别写错）
sudo umount /dev/sdb? 2>/dev/null || true
sudo dd if=<镜像路径>.img of=/dev/sdb bs=4M conv=fsync status=progress
sudo sync
lsblk                                  # 应看到分区出现
```

> Windows 图形烧录用 balenaEtcher / Rufus（DD 模式）也可。

### 2.3 启动并观察串口 / 显示

1. SD 插板 → 接 **UART2 串口（1500000 8N1）** 或 HDMI → 接 5V 电源。
2. 观察启动日志的**关键节点**，逐个指认（这是面试必问）：

```text
U-Boot 202x ...          ← Bootloader（第二阶段启动）
=> 设备树加载 / DTB       ← Device Tree Blob
Starting kernel ...      ← 内核接管
登录提示                  ← 根文件系统挂载完成
```

### 2.4 进入系统后的验证清单（每条都要能解释）

```bash
uname -a                 # 内核版本 + aarch64
cat /etc/os-release      # 发行版身份
lsblk                    # 分区结构（boot / rootfs）
dmesg | grep -iE 'error|fail' | head    # 有没有明显报错
ip a && ip route         # 网络是否起来
lsmod | grep rknpu       # NPU 驱动是否加载（后续 AI 用）
ls -l /dev/rknpu
```

**验证标准**：你能不看文档，讲清楚「上电后从 ROM → BootROM → U-Boot(TPL/SPL) → ATF → 内核 → rootfs」这条链每一步干了什么。

**面试话术**：「我先在 ROCK 5C 上亲手烧录并启动了系统，用串口观察了 U-Boot、设备树、内核、rootfs 的完整启动节点，最后验证了 NPU 驱动和网络。」

## 3. 阶段 1：USB UVC 摄像头采集链路（P0 核心，1.5–2 天）

目标：这是 JD 里**出现频率最高**的技术点（职责 5/6、要求 7、优先考虑一整列：V4L2 / UVC / GStreamer / 硬件编解码）。必须亲手从「枚举设备」一路跑到「硬编 H.264 落盘」。

### 3.1 枚举设备

```bash
lsusb | grep -i cam                  # 期望出现 UVC 摄像头（如 Logitech Webcam C270）
sudo apt install -y v4l-utils
v4l2-ctl --list-devices              # 期望列出 /dev/video0 与 /dev/media0
```

### 3.2 查看并设置格式

```bash
v4l2-ctl -d /dev/video0 --list-formats-ext    # 看支持的 YUYV / MJPG 与分辨率帧率

v4l2-ctl -d /dev/video0 --set-fmt-video=width=1280,height=720,pixelformat=YUYV \
         --stream-mmap --stream-count=1 --stream-to=/tmp/test.yuv
ls -lh /tmp/test.yuv                 # 抓到一帧 YUYV 原始帧（非 0 即链路通）
```

### 3.3 装 Rockchip MPP 硬编插件

```bash
sudo apt install -y gstreamer1.0-tools gstreamer1.0-plugins-base \
     gstreamer1.0-plugins-good gstreamer1.0-plugins-bad \
     gstreamer1.0-plugins-ugly gstreamer1.0-rockchip1 \
     librockchip-mpp1 librga2 librockchip-vpu0

gst-inspect-1.0 | grep -i mpp        # 期望看到 mpph264enc / mpph265enc / mppjpegenc
```

### 3.4 采集 → 硬编 → 落盘（完整链路）

```bash
gst-launch-1.0 -e \
    v4l2src device=/dev/video0 ! \
    video/x-raw,width=1280,height=720,framerate=15/1,format=YUY2 ! \
    videoconvert ! video/x-raw,format=I420 ! \
    mpph264enc ! h264parse ! mp4mux ! \
    filesink location=/tmp/test_720p.mp4

ls -lh /tmp/test_720p.mp4            # 有 MP4 产出
top -d 1                             # 编码进程 CPU 应接近 0%（硬件编码证据）
```

### 3.5 必背的底层概念（每个都要能讲清「它管什么 / 长什么样」）

- **V4L2**：视频设备用户态 API（open/ioctl/mmap/streamon）。
- **Media Controller**：把 sensor → CSI → ISP → video 节点连成媒体图（`/dev/media0`，`media-ctl -p`）。
- **UVC**：免厂商驱动的 USB 标准视频类，内核 `CONFIG_USB_VIDEO_CLASS=y`。
- **MPP/VEPU**：RK3588 硬件视频编码单元，GStreamer 用 `mpph264enc` 走硬编，CPU 几乎 0 占用，缩放用 RGA。
- **DRM/KMS（显示）** 与 **ALSA（音频）** 各自边界（JD 要求 7 原话，要能一句话定位）。

**验证标准**：能面对屏幕讲清「数据从摄像头传感器 → USB/UVC → V4L2 `/dev/video0` → GStreamer → MPP 硬编 → MP4」的每一跳。

**面试话术**：「我在 ROCK 5C 上用 USB UVC 摄像头，通过 V4L2 打开 `/dev/video0`、设置 720p/YUY2 格式，再用 GStreamer 调 Rockchip MPP 的 `mpph264enc` 做硬件 H.264 编码，实测 CPU 占用接近 0%。」

## 4. 阶段 2：亲手跑通 cat-monitor 应用（1 天）

目标：把 AI 写的代码变成**你理解并跑通**的东西，重点是读懂核心状态机，而不是背代码。

### 4.1 进入工作区并跑测试

```bash
cd /home/wbh808/cat-monitor-grok46
ls                                     # 先看目录结构，确认 Makefile 与 src 位置
make test                              # 15 项单元测试（含 IDLE→CANDIDATE→ACTIVE 状态机）
make sim                               # 合成画面写出 eat + drink
make deb                               # 产出 cat-monitor-grok46_1.0.0_arm64.deb
```

### 4.2 读透状态机（这是面试展开的核心）

把状态机测试代码读一遍，能画出并用嘴讲：

```text
IDLE（无目标）→ 运动门控触发 → CANDIDATE（候选）→ 连续 N 帧命中 → ACTIVE（进食/饮水）
ACTIVE → 连续 M 帧离开（迟滞防抖）→ COOLDOWN → 回 IDLE
事件 ACTIVE 期间才启动录制；预录 5–10s、中断 10s 内续录。
```

### 4.3（时间允许）把 deb 装上板跑主服务

```bash
scp image/debs/cat-monitor-grok46_1.0.0_arm64.deb radxa@<板IP>:~
ssh radxa@<板IP> "sudo dpkg -i cat-monitor-grok46_1.0.0_arm64.deb"
systemctl --user status cat-monitor 2>/dev/null || ./cat_camera.py --help
```

**验证标准**：你能**不用笔记**画出上面的状态机，并解释「空间（猫头在碗区/水区 ROI）+ 时间（连续帧迟滞）」两点怎么联合判断进食/饮水。

## 5. 阶段 3：BSP 内核定制最小闭环（1 天，可降级为「读+讲」）

目标：JD 职责 2「Bootloader / Kernel / Device Tree / 驱动移植配置」需要一个**你亲手做过的动作**，即便只是加一个驱动选项。

### 5.1 最小闭环（推荐只做这一步）

```bash
cd /home/wbh808/bsp
# 看一眼内核配置入口 kconfig.conf，找到某个你关心的开关（如 CONFIG_USB_VIDEO_CLASS）
grep -n "VIDEO_CLASS\|RKNPU" .src/linux/arch/arm64/configs/* 2>/dev/null | head

# 重新构建内核（进程可能较久，后台跑）
./bsp --no-prepare-source linux rk2410 rock-5c -r 999
```

产出 `linux-image-*.deb` 后，装板验证：

```bash
sudo dpkg -i linux-image-*.deb linux-dtb-*.deb
sudo update-initramfs -c -k all
sudo reboot
```

### 5.2 必背概念（面试直接问）

- **Device Tree**：dts/dtsi、节点、`compatible`、overlay 是干嘛的、为什么内核和硬件要解耦。
- **内核模块**：`insmod`/`modprobe`、驱动如何被内核调用、device driver model。
- **补丁固化**：bsp 里 `fork.conf`（仓库/分支）、`kconfig.conf`（内核配置）、补丁目录各管什么。

> ⚠️ 若时间不够：这个阶段不硬刷构建，降级为「照着文档 01 读 + 能讲清楚 bsp 的四个输入（fork.conf / kconfig.conf / 补丁 / profile）」。**不要**为了「跑过一遍」而占掉阶段 1 的时间。
