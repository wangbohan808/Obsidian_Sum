## 1. 移植目标与总体思路

把原先「单 `while(1)` 轮询」的集尘宝固件，改成可调度、可阻塞、可抢占的 FreeRTOS 应用，同时满足：

| 目标 | 做法 |
|------|------|
| 业务功能不变 | 硬实时红外 / LED 仍留在 ATIM 100µs、SysTick 1ms 中断 |
| 逻辑可并行 | 主循环拆成 `monitor` / `comm` / `dust` 三个任务 |
| 事件驱动集尘 | `need_duty=1` 改为「置位 + 任务通知」，dust 空闲时阻塞不空转 |
| 共享状态安全 | 递归互斥锁保护跨任务访问的业务变量 |
| 4KB RAM 能装下 | 静态创建任务 / 锁 / 队列，heap 仅 256 字节兜底 |
| 可调试体验 RTOS 性质 | 优先级抢占、通知、队列、`vTaskDelay(Until)` 均可在 VS Code 里观察 |

**总体原则：**

1. **先能跑内核，再拆任务** —— 不要一次把业务全改完再编译。  
2. **中断里的硬实时不动** —— 只把主循环里的“软实时业务”搬进任务。  
3. **标志位轮询 → 同步原语** —— 轮询 `need_duty` 改为通知唤醒；跨任务共享数据加锁。  
4. **静态分配优先** —— CW32L010 仅 4KB RAM，动态 `malloc` 不可作为主路径。

## 2. 裸机架构 vs RTOS 架构对照

### 2.1 裸机（移植前）

```text
main()
  ├─ 时钟 / InitTick / 硬件初始化
  ├─ Timer_Task_Init()   ← 注册 100µs / 1ms 中断回调
  └─ while (1) {
         dust_mode_check_and_switch();
         pole_decoder_process();
         if (need_duty) dust_absorption_ctrl();   ← 忙等轮询
         base_self_detect();                      ← 内含喂狗
     }

ATIM_IRQHandler  (100µs)  → 红外引导 / 极柱捕获 / LED
SysTick_Handler  (1ms)    → tick_ms_num++ / 1ms 业务回调
```

触发集尘的方式：业务里直接写 `need_duty = 1`，主循环下一圈看到再跑集尘。

### 2.2 RTOS（移植后）

```text
main()
  ├─ 时钟 / InitTick / 硬件 / Timer_Task_Init / dust_mode_init
  ├─ app_rtos_init()          ← 创建递归互斥锁 + 事件队列
  ├─ xTaskCreateStatic × 3    ← monitor / comm / dust
  ├─ app_rtos_set_dust_task() ← 登记通知目标句柄
  └─ vTaskStartScheduler()    ← 之后永不返回

                 ┌──────────── ATIM / SysTick ISR ────────────┐
                 │ 红外 / 极柱 / LED / 1ms 业务 + FreeRTOS tick │
                 └────────────────────────────────────────────┘
                                      │
          ┌───────────────────────────┼───────────────────────────┐
          ▼                           ▼                           ▼
   [dust  prio3]               [monitor prio2]              [comm prio1]
   等通知→集尘                   5ms 自检+喂狗                 1ms 解码
   ↑ xTaskNotifyGive             → 队列投递事件                 ← 队列取事件
          │                           │                           │
          └──────────── app_lock (递归互斥锁) ────────────────────┘
```

| 裸机写法 | RTOS 写法 |
|----------|-----------|
| `while(1)` 里顺序调所有函数 | 拆成独立任务循环 |
| `need_duty = 1` | `app_request_dust()`（置位 + 通知） |
| 主循环轮询 `if(need_duty)` | dust 任务 `ulTaskNotifyTake` 阻塞等待 |
| 无同步 | `app_lock` / `app_unlock` 保护共享状态 |
| 忙等占满 CPU | `vTaskDelay` / `vTaskDelayUntil` 让出 CPU |

## 4. 阶段 A：引入 FreeRTOS 内核源码

### 4.1 获取源码

本工程做法：将官方 FreeRTOS-Kernel 放到资源目录，再精简拷贝到实际参与编译的路径：

```text
CW32L010_APP/
├── Resource/FreeRTOS-Kernel-main/     # 完整上游树（参考用，可不参与编译）
└── Middlewares/FreeRTOS/              # 真正编进固件的精简内核
```

也可从 [FreeRTOS/FreeRTOS-Kernel](https://github.com/FreeRTOS/FreeRTOS-Kernel) 直接下载对应版本。

### 4.2 需要参与编译的最小文件集

| 类别 | 路径 | 说明 |
|------|------|------|
| 核心 | `tasks.c` `queue.c` `list.c` | 调度、队列/互斥、链表 |
| 堆 | `portable/MemMang/heap_4.c` | 动态分配兜底（本工程几乎不用） |
| 移植层 | `portable/GCC/ARM_CM0/port.c` | tick、临界区、启动调度 |
| 移植汇编 | `portable/GCC/ARM_CM0/portasm.c` | PendSV / SVC 上下文切换 |
| 头文件 | `include/*` + `portable/GCC/ARM_CM0/portmacro.h` | API 与 port 宏 |

**可选、本工程关闭：**

- `timers.c` —— `configUSE_TIMERS = 0`，不编入
- `event_groups.c` / `stream_buffer.c` / `croutine.c` —— 未使用

### 4.3 为何选 `GCC/ARM_CM0`

- CW32L010 是 **Cortex-M0+**，对应官方 `ARM_CM0` 移植。
- 工具链虽是 AC6 (armclang)，但该 GCC 移植层用的是标准 CMSIS 内联汇编 / 属性，**可被 armclang 编译**。
- 曾尝试 `RVDS/ARM_CM0`，与 AC6 不兼容，最终改回 GCC 移植。
- 启动文件里的弱符号 `SVC_Handler` / `PendSV_Handler` 会被 `portasm.c` 强符号覆盖，无需改 startup。

### 4.4 推荐目录布局（落地后）

```text
CW32L010_APP/Middlewares/FreeRTOS/
├── tasks.c
├── queue.c
├── list.c
├── include/
│   ├── FreeRTOS.h
│   ├── task.h
│   ├── queue.h
│   ├── semphr.h
│   └── ...
└── portable/
    ├── GCC/ARM_CM0/
    │   ├── port.c
    │   ├── portasm.c
    │   ├── portasm.h
    │   └── portmacro.h
    └── MemMang/
        └── heap_4.c
```

配置头文件放在应用侧：

```text
CW32L010_APP/App/FreeRTOSConfig.h
```

内核通过 include 路径找到它（`#include "FreeRTOSConfig.h"`）。

## 5. 阶段 B：编写 FreeRTOSConfig.h

本工程关键配置要点如下（完整文件见 `CW32L010_APP/App/FreeRTOSConfig.h`）。

### 5.1 时钟与调度

```c
#define configCPU_CLOCK_HZ       48000000UL   /* 与 SYSCTRL_HSI 一致 */
#define configTICK_RATE_HZ       1000         /* 1ms tick，与原 SysTick 对齐 */
#define configUSE_PREEMPTION     1            /* 抢占式 */
#define configUSE_TIME_SLICING   1
#define configMAX_PRIORITIES     5            /* 本工程用到 1/2/3 + Idle */
```

### 5.2 内存：静态为主

```c
#define configSUPPORT_STATIC_ALLOCATION   1
#define configSUPPORT_DYNAMIC_ALLOCATION  1
#define configTOTAL_HEAP_SIZE             ( ( size_t ) ( 256 ) )
#define configKERNEL_PROVIDED_STATIC_MEMORY 1  /* Idle 任务静态内存由内核提供 */
```

任务 TCB/栈、互斥锁、队列全部 `*Static` 创建，heap 只防意外动态调用。

### 5.3 打开用到的原语，关掉不用的

```c
#define configUSE_MUTEXES              1
#define configUSE_RECURSIVE_MUTEXES    1   /* 必须：业务里可能嵌套加锁 */
#define configUSE_TASK_NOTIFICATIONS   1
#define configUSE_TIMERS               0
#define configUSE_EVENT_GROUPS         0
```

```c
#define INCLUDE_vTaskDelay             1
#define INCLUDE_xTaskDelayUntil        1
#define INCLUDE_vTaskSuspend           1
#define INCLUDE_xTaskGetSchedulerState 1   /* SysTick 合流里要判断是否已启动 */
```

### 5.4 调试钩子（4KB 板子强烈建议开）

```c
#define configCHECK_FOR_STACK_OVERFLOW  2
#define configUSE_MALLOC_FAILED_HOOK    1
```

在 `main.c` 实现 `vApplicationStackOverflowHook` / `vApplicationMallocFailedHook`（关中断死循环，便于断点抓住）。

### 5.5 关键：把内核 SysTick 改名

GCC/ARM_CM0 的 `port.c` 会定义 `SysTick_Handler`。本工程板级已有同名入口（要跑 `timer_ms` 和 1ms 业务），必须冲突消解：

```c
/* FreeRTOSConfig.h 末尾 */
#define SysTick_Handler    xPortSysTickHandler
```

效果：编译 `port.c` 时，其 `SysTick_Handler` 实际变成 `xPortSysTickHandler`；真正的向量入口仍由 `BSP/tim_cfg.c` 提供。

## 7. 阶段 D：SysTick 与内核 tick 共存

这是本移植**最关键、也最容易踩坑**的板级改动。

### 7.1 问题

| 角色 | 需要什么 |
|------|----------|
| 原业务 | `SysTick_Handler` 里 `tick_ms_num++`、`hal_timer_run(1ms)` |
| FreeRTOS | 同样依赖 1ms SysTick 做 `xTaskIncrementTick` |
| 冲突 | 不能有两个 `SysTick_Handler` 符号 |

### 7.2 解法（本工程落地）

**步骤 1** — `FreeRTOSConfig.h` 把 port 里的处理函数改名为 `xPortSysTickHandler`（见 §5.5）。

**步骤 2** — `BSP/tim_cfg.c` 保留真正的向量入口，并在调度器启动后转发：

```c
#include "FreeRTOS.h"
#include "task.h"

/* 取消 FreeRTOSConfig 里的改名宏，否则本文件也写不出真正的 SysTick_Handler */
#undef SysTick_Handler
extern void xPortSysTickHandler(void);

void SysTick_Handler(void)
{
    tick_ms_num++;
    hal_timer_run(HAL_TIMER_INDEX_1MS);

    if( xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED )
    {
        xPortSysTickHandler();
    }
}
```

**要点：**

1. **必须 `#undef SysTick_Handler`**，否则本文件定义的也是 `xPortSysTickHandler`，向量表仍指向弱符号空函数。  
2. **调度器未启动前不要调** `xPortSysTickHandler()`：`main` 里 `InitTick` 已开 SysTick，此时若调内核 tick 会访问未初始化的调度器状态。  
3. `timer_ms()` 读 `tick_ms_num` 时关中断，避免与 ISR 撕裂（多任务下更必要）。

### 7.3 ATIM 100µs：保持不动

`ATIM_IRQHandler` 仍只跑 `hal_timer_run(HAL_TIMER_INDEX_100US)`。  
红外引导、极柱捕获、LED 正常模式控制等**硬实时**逻辑继续在中断里，不被任务调度抖动影响。

## 8. 阶段 E：业务逻辑 RTOS 化

### 8.1 任务划分原则

对照裸机主循环职责，按「周期 / 事件 / 通信」拆分：

| 任务 | 优先级 | 周期/触发 | 承接的裸机逻辑 |
|------|--------|-----------|----------------|
| `dust` | 3（最高） | 任务通知唤醒 | `if(need_duty) dust_absorption_ctrl()` |
| `monitor` | 2 | 5ms `vTaskDelayUntil` | `base_self_detect()`（含喂狗）+ 上座/离座事件 |
| `comm` | 1（最低） | 1ms `vTaskDelay` | `dust_mode_check_and_switch()` + `pole_decoder_process()` + 消费事件 |

**为何 dust 最高：** 集尘状态机对实时性更敏感，一旦被请求应能打断解码等低优先级工作。  
**为何硬实时不进任务：** 100µs 级红外时序无法承受任务切换抖动。

### 8.2 main 启动流程（对照）

**裸机：**

```c
Hardware_init();
Timer_Task_Init();
dust_mode_init();
while (1) { /* 全部业务 */ }
```

**RTOS：**

```c
Hardware_init();
Timer_Task_Init();
dust_mode_init();
app_rtos_init();

xTaskCreateStatic(monitor_task, ...);
xTaskCreateStatic(comm_task, ...);
dust_handle = xTaskCreateStatic(dust_task, ...);
app_rtos_set_dust_task(dust_handle);   /* 必须在 StartScheduler 前 */

vTaskStartScheduler();
for (;;) { }   /* 正常不会到这里 */
```

### 8.3 三个任务伪代码

```c
/* monitor：固定节拍自检 + 生产事件 */
void monitor_task(void *arg) {
    TickType_t last_wake = xTaskGetTickCount();
    for (;;) {
        vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(5));
        app_lock();
        base_self_detect();
        /* 若 dock 状态变化 → unlock 后 app_evt_send(...) */
        app_unlock();
    }
}

/* comm：周期解码 + 非阻塞消费事件 */
void comm_task(void *arg) {
    for (;;) {
        while (app_evt_recv(&evt, 0) == pdPASS) { /* 处理事件 */ }
        app_lock();
        dust_mode_check_and_switch();
        pole_decoder_process();
        app_unlock();
        vTaskDelay(pdMS_TO_TICKS(1));
    }
}

/* dust：阻塞等待 → 高优先级跑集尘 */
void dust_task(void *arg) {
    for (;;) {
        app_wait_dust_request(portMAX_DELAY);   /* 睡死，不空转 */
        while (need_duty) {
            app_lock();
            dust_absorption_ctrl();
            app_unlock();
            vTaskDelay(pdMS_TO_TICKS(1));       /* 缓启动忙等时让出 CPU */
        }
        app_evt_send(APP_EVT_DUST_DONE);
    }
}
```

### 8.4 新增 `app_rtos` 封装层

集中三种同步原语，避免业务文件到处裸调 FreeRTOS API：

| API | 底层 | 用途 |
|-----|------|------|
| `app_lock` / `app_unlock` | 递归互斥锁 `xSemaphoreCreateRecursiveMutexStatic` | 保护共享状态 |
| `app_request_dust` / `app_wait_dust_request` | `xTaskNotifyGive` / `ulTaskNotifyTake` | 一对一唤醒集尘 |
| `app_evt_send` / `app_evt_recv` | 静态队列（深度 4） | 离散事件传递 |

**为何递归互斥锁：**  
`monitor` 持锁调用 `base_self_detect()` 时，内部可能再调 `app_request_dust()` → 再次 `app_lock()`。普通 mutex 会自死锁；递归 mutex 允许同任务嵌套。

**为何通知而不是信号量唤醒 dust：**  
一对一、无额外对象、更轻；适合“有人点名开始集尘”。

源文件：

- `CW32L010_APP/App/app_rtos.h`
- `CW32L010_APP/App/app_rtos.c`

### 8.5 `app_request_dust` 替代裸写标志

```c
void app_request_dust(void)
{
    app_lock();
    need_duty = 1;
    app_unlock();

    if( s_dust_task != NULL )
        (void)xTaskNotifyGive(s_dust_task);
}
```

相对裸机多做了两件事：持锁写标志 + 唤醒等待中的 dust 任务。

## 9. 阶段 F：业务调用点改造清单

内核与任务骨架就绪后，把「写标志」改成「请求集尘」。业务状态机本身（`dust_absorption_ctrl` 等）可基本保持原样。

### 9.1 必须改的文件

| 文件 | 裸机 | RTOS |
|------|------|------|
| `App/main.c` | `while(1)` 轮询全部业务 | 三任务 + `vTaskStartScheduler` |
| `App/base_self_det.c` | `need_duty = 1` | `#include "app_rtos.h"` + `app_request_dust()` |
| `App/func_pole_decoder.c` | 多处 `need_duty = 1` | 改为 `app_request_dust()` |
| `BSP/tim_cfg.c` | 仅业务 SysTick | 合流 `xPortSysTickHandler` |
| （新增）`App/app_rtos.c/.h` | 无 | 锁 / 通知 / 队列 |
| （新增）`App/FreeRTOSConfig.h` | 无 | 内核配置 |

### 9.2 基本不动的部分

| 模块 | 原因 |
|------|------|
| `func_dust_collect.c` 状态机 | 仍由 dust 任务调用；清零 `need_duty` 逻辑保留 |
| `func_ir_ack` / `func_docking_guide` / `func_led_tasks` | 仍挂在中断时间片 |
| `ATIM_IRQHandler` | 100µs 硬实时不变 |
| `Hardware_init` / `Timer_Task_Init` | 初始化顺序与注册表基本不变 |
| BootLoader 工程 | 与 APP 独立，本次不移植 RTOS |

### 9.3 典型 diff 示意（自检触发集尘）

```c
/* 裸机 */
need_duty = 1;

/* RTOS */
app_request_dust();   /* 内部：need_duty=1 + NotifyGive */
```

产测路径（`func_pole_decoder.c`）同样三处替换即可。

### 9.4 喂狗位置

裸机：`base_self_detect()` 末尾 `IWDT_Refresh()`。  
RTOS：该函数仍由 **monitor 任务每 5ms** 调用，喂狗节奏与原来相近；无需单独看门狗任务（除非以后 monitor 可能长时间阻塞）。

### 9.5 调试串口延后初始化

原在主循环里「上电 20s 后开 UART」的逻辑，移到 **comm 任务** 循环中，行为保持一致。

## 11. RAM / 栈 / 堆预算

CW32L010 仅 **4KB RAM**，必须精打细算。

### 11.1 本工程任务栈（单位：字 = 4 字节）

| 任务 | 栈字数 | 约占用 |
|------|--------|--------|
| monitor | 72 | 288 B |
| comm | 80 | 320 B |
| dust | 96 | 384 B |
| Idle（内核静态） | `configMINIMAL_STACK_SIZE`=64 | 256 B |

外加各 TCB、递归 mutex 控制块、队列控制块与 4 槽事件缓冲、heap 256B，以及原有 `.bss`/`.data`。

### 11.2 经验规则

1. 先开 `configCHECK_FOR_STACK_OVERFLOW=2`，栈不够会进 hook。  
2. dust 缓启动里有短忙等路径，栈略给大；仍不够再逐个加，**不要一次性开很大**。  
3. 链接报 `No space` / RW 段溢出时：减栈、关未用内核模块、压缩全局缓冲，而不是开大 heap。  
4. 任务 / 锁 / 队列坚持 `*CreateStatic`，避免碎片与不可控动态增长。

## 13. 踩过的坑与对策

| 现象 | 根因 | 对策 |
|------|------|------|
| 链接重复定义 `SysTick_Handler` | port 与 BSP 各定义一份 | `FreeRTOSConfig.h` 宏改名为 `xPortSysTickHandler` |
| `timer_ms` 不走、1ms 业务停 | 只保留了 port 的 SysTick，或 BSP 里忘了 `#undef` | BSP 提供真正入口并 `#undef` 后再定义 |
| 启动即 HardFault / 调度异常 | 调度器未启动就调了 `xPortSysTickHandler` | 用 `xTaskGetSchedulerState()` 判断 |
| 任务创建失败 / RAM 溢出 | 栈过大或动态对象过多 | 静态创建 + 压缩栈 + 关 timers |
| dust 收不到通知 | 句柄登记晚于首次 `NotifyGive` | `vTaskStartScheduler` 前 `app_rtos_set_dust_task` |
| 持锁后再 `app_request_dust` 卡死 | 用了普通 mutex | 改用递归互斥锁 |
| AC6 编不过 RVDS port | 内联汇编方言不兼容 | 改用 `portable/GCC/ARM_CM0` |
| 单步“跑飞” | 中断插入或优化 | Debug `-O0`；对阻塞 API 用断点而非单步跨过 |
