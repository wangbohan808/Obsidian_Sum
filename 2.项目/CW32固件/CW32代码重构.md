# CW32代码重构

## 📅2026-09-10

## 项目背景

这是一个与扫地机器人配套的基站项目，主要功能是引导扫地机的回充、集尘；
原本使用的是国民技术的N32G003芯片，为了节省成本，在保证基础功能不变的情况下衍生出一款新的基站产品，使用CW32l010主控，并且砍掉了一颗红外接收灯
--去年年底，此背景下，我独立完成了代码的移植，以及框架优化重构


## 架构优势

旧的代码因为在开发过程中不断进行打补丁，各个模块之间嵌套很严重，文件分类也不是很合理，明明是一个功能却拆分到几个文件，其中还添加了很多标志位，在阅读的时候觉得逻辑很混乱



我的逻辑框架主要分为三部分：
芯片厂商提供的HAL库->使用芯片库配置的BSP层，比如这个项目这款板子使用哪些定时器、uart引脚进行配置；使用HAL实现的呼吸灯、灯闪烁等基础功能-->app层就是根据这个项目的实际业务逻辑进行划分文件，回充、集尘、红外发码、极片通讯解码

去除冗余的标志位，全局根据两个个枚举类型决定机器状态，执行对应功能：
机器人是否在充电桩上-->决定是发送引导码还是开始极片通讯的解码
尘袋是否在位-->影响灯显状态以及集尘功能执行

还有一个逻辑，我希望下层代码尽量不使用上层代码，实现分层，但是有一个问题是--无论是灯显、还是发码功能，都需要借助定时器功能进行执行，这样必须要下层bsp调用app层封装的函数

实现一个时间片逻辑：
1. 储存回调函数结构体--已经执行的次数、这个回调函数多少次调用执行一次
2. 定时器结构体：嵌套回调函数结构体、限制注册的回调函数数量


hal_timer_task_register：在数组中找到空闲位置放置回调函数----app层注册任务函数，在bsp的定时器中定时执行
hal_timer_run：定时执行，每执行一次将所有的结构体，各个回调函数的计数+1，与回调函数注册的时候设置的计数比较，到达后执行并清零计数


为什么设置两个定时器：
1. 有一个1ms的定时器，用于系统时钟，给全局需要时间的位置提供一个ms计时
2. 但是红外发码等任务，要求100us进行一次计数，计数7次发送一个红外码，系统定时器精度不够

不重要的500ms一次的灯显翻转的任务可以放在ms定时器里，可以节省一点CPU的资源
如果需要的话，可以通过不同的定时器，设置不同的中断优先级，保证重要任务的准确执行




## 关键功能

在主循环中进行自检任务：
1. 根据adc值的高低判断机器人是否在位、读取尘袋在位检测器的电平决定尘袋是否在位--从而修改两个枚举值状态



## 红外发码

定时器控制发送38kHz载波，四路红外灯作为门控---
标准红外一体化接收头：频率对不上，接收头输出会很弱甚至没有---这样解码结果更加稳定


每个灯有一个专属一字节码值，在进行发码时，一字节中的每一位会被扩充为5个符号  1->10000 0->11110，每一个符号在100us定时器计数保持计数7次发送下一位，一帧约28ms，随后关闭所有灯，计数器清零等待发送下一帧


## 极片解码

机器人在位是保持高电平-->扫地机发送低电平信号，对应的adc检测，如果拉低200ms低电平，400ms左右高电平，再低电平触发集尘
--此时时间低电平没有到离座的计数



## 风机集尘

根据交流电的过零检测进行缓启动

## 计算定时器周期内的时钟周期

- 进行单位换算：48M单位换算为us，就是每us有48个周期，100us定时器就是执行4800个指令


**每种基础动作有其时钟周期拍数：**

Cortex-M0+ 上，不必反汇编也能估数量级。用下面这张表（含 Flash 等待，按偏保守算）：

|动作|大约拍数|约合时间|
|---|---|---|
|整数加减、比较、位运算|1～3|< 0.1µs|
|读/写一个寄存器（含 GPIO）|2～6|< 0.15µs|
|`if` / `switch` 一次（含跳转）|4～12|< 0.3µs|
|空函数调用（进+出）|15～30|~0.5µs|
|带几个参数的函数调用|20～50|~1µs|
|ADC 读一次结果寄存器|10～30|~0.5µs|
|短循环，转一圈|6～15 × 圈数|—|
|除法、取模、64 位运算|几十～上百|数 µs 量级|

**定时器中任务拍数估计：**

按源码结构，粗估是：

|任务|多数拍在干什么|粗估|
|---|---|---|
|`dust_fan_phase_task`|`switch` + 减 1，偶而写一次 GPIO|平时 40～120 拍（1～2.5µs）；翻脚那拍略高|
|`led_normal_mode_control`|两三层 `if`，再调灯函数|80～250 拍（2～5µs）|
|`pole_detect_capture`|早退只要一个 `if`；否则读 ADC + 移位|早退 30～80 拍；采样 150～400 拍（3～8µs）|
|`ir_docking_guide_send`|多数拍：计数 + 四路 IO；`count==1` 时做 8 次调制循环|平时 100～300 拍；调制那拍 400～800 拍（8～17µs）|

四个加在一起，多数拍大概 几百拍（不到 10µs）；最坏那一拍（引导码刚开始调制）也许到 十几 µs，仍然远小于 100µs 的 4800 拍。

## 关于嵌入式的一点理解

- 我是觉得无论是MCU还是RTOS还是Linux最底层的原理是大体一致的，RTOS以及Linux只是在MCU之上封装了一些功能
- 关于实时性，MCU也可以实现实时性，使用多个定时器中断，不同优先级放置不同的定时器中断中
- RTOS任务注册机制，MCU通过书写回调函数完成时间片也可以进行实现
- 最本质都是CPU进行取指，执行；不过MCU通直接在FLASH进行取值，Linux在此之上封装了一个虚拟空间地址概念，将指令从ROM搬运到RAM内存进行执行

MCU 裸机、RTOS、Linux 底层硬件原理一致：都依靠 CPU 取指译码执行，依靠中断改变执行流。RTOS 与 Linux 本质是在 CPU 硬件之上封装的软件层。

裸机 MCU 依靠多优先级定时器中断，能够实现一定程度的实时响应，但只有中断上下文可以抢占；裸机也可以手写回调 + 定时器节拍，实现简易协作式多任务，但没有独立任务栈，不支持抢占。RTOS 在内核中实现抢占式调度，靠节拍中断保存 / 恢复任务上下文，每个任务拥有独立栈，解决多任务并发与硬实时需求。

代码存储上：MCU 程序默认存 Flash 并可直接在 Flash 取指执行，运行时数据拷贝到 RAM；而带 MMU 的 Linux 引入虚拟地址空间，由加载器将程序从存储介质（Flash / 磁盘）载入 RAM 执行，MMU 负责地址翻译与内存隔离，这是 MCU 和 RTOS 大多不具备的能力。



- 我认为RTOS与Linux这些系统，就是在原有硬件逻辑的基础之上，面对特定的场景，封装一些更好用的接口，方便开发者使用，但底层的硬件机制，CPU调度取值执行，使用内存资源大体是类似的；切换上下文使用更多指针、更多栈，从而实现不同任务、线程调度；
- linux进程就是资源划分更加隔离，不仅有不同的栈，还有不同的堆资源、不同的地址页，对应独立的虚拟地址空间
