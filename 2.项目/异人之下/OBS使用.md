# 概念理解

## 分辨率

**基础概念：** 横向像素 × 纵向像素


**画布比例与显示器硬件比例不匹配处理方法：**

1. **加黑边（Letterbox / Pillarbox，保留完整画面，不变形）⭐最稳妥**
播放器把整个画面完整放进去，空白区域填充黑色。
   - 横内容放到更宽的屏：上下黑边（Letterbox，信箱模式）
   例：16:9 视频放到 21:9 超宽显示器，上下黑条
   - 横内容放到竖屏手机：左右黑边（Pillarbox，邮筒模式）
   例：16:9 直播画面直接在抖音竖屏播放器里，左右黑边
   ✅特点：**画面所有信息都保留，无裁切，不变形**，只是有黑条
2. **裁边（Crop / Zoom，铺满屏幕，丢掉一部分画面）⭐短视频平台最爱**
播放器放大画面，直到刚好填满屏幕的长和宽，超出屏幕范围的画面直接切掉。
例：抖音默认模式，把 16:9 直播源裁成 9:16 竖屏，画面左右被砍掉一大块
✅特点：**屏幕完全填满，没有黑边，但是画面信息丢失**，人物 / UI 容易被裁掉
3. **拉伸（Stretch，强行铺满，不推荐）**
直接不等比例缩放，宽和高各自拉到屏幕边界，画面压扁或者拉长，人物变形。
✅特点：无黑边、不裁切，但是几何失真，几乎正规平台都禁用这个模式


**常见纵横比：**
- 16:9：1920×1080、3840×2160（4K）、1280×720，主流直播、视频、显示器
- 16:10：1920×1200、2560×1600，很多笔记本屏幕
- 3:2：3072×1920（你截图里显示器 2 就是这个！平板 / 笔记本常见）
- 9:16：1080×1920，手机竖屏短视频

**画面精细程度：** PPI（像素密度，每英寸像素数）

PPI = 一英寸的屏幕里面塞了多少个像素点---对角线单位长度像素点个数

- 同样 1920×1080：放在 24 寸显示器，PPI≈92；放在 5 寸手机，PPI≈440。
👉 这就是为什么手机屏幕看着无比细腻，大屏显示器颗粒感更明显：**分辨率一样，屏幕越小 PPI 越高**。
✅ PPI 描述的是**屏幕硬件的精细程度，和视频文件本身分辨率无关**。

> 
> 一个 1080P 视频，放到 4K 高 PPI 手机上播放，视频本身还是 1080 个像素行，只是屏幕把这 1080 行像素**放大铺开**到 4K 屏幕上显示。


**分辨率流向：**

```text
【游戏/摄像头渲染分辨率】 → 【OBS画布分辨率（渲染画板）】→（OBS重采样缩放）→【输出码流分辨率（推流/录像）】
                                                                 ↓（网络传输）
【观众端设备：手机/电脑/电视播放器】 → 播放器缩放，适配观众屏幕的原生分辨率 + 屏幕物理大小
```


**更改“系统分辨率（显示分辨率）”：**
改【显示分辨率】= 改变显卡输出图像大小，由显示器硬件来缩放适配面板

> 这个选项，控制的是：**显卡渲染出来、发给显示器的图像，是多少像素**。
> 不是屏幕本身的像素，是显卡输出的信号尺寸。

**场景 A：系统分辨率 = 原生分辨率（3072×1920）**
显卡输出一张 3072×1920 的图；显示器面板刚好 3072×1920。
👉 **点对点映射**：信号里每 1 个像素，对应面板上 1 个物理像素。
没有插值、没有缩放，画面最锐利、清晰。

**场景 B：你手动把系统分辨率改成 1920×1080（≠原生）**
显卡现在只渲染一张 1920×1080 的图像，发给显示器。
但是你的屏幕硬件有 3072×1920 个物理点，放不下这个 1:1。
**显示器内部的 SCALER（屏幕缩放芯片），会把这张小图放大拉伸，铺满整个 3072×1920 面板**。
放大的时候，原图信息不够，芯片要插值计算出新像素，所以画面发虚、模糊。



### ”显示分辨率“与”DPI缩放“：
- 修改【显示分辨率】：改变**最终显卡输出**整张图的大小 → 显示器硬件缩放 → 全局变糊
- 修改【DPI 缩放】：显卡输出整张图大小不变（3072×1920），只是 UI 程序的绘制坐标被系统放大 → 屏幕硬件仍然点对点，桌面图标文字本身是清晰的

**显示分辨率 = 显卡生成一张图像，这张图有多少宽 × 高像素，然后发给显示器。** 显示器面板是固定：你的屏是 3072px（宽） × 1920px（高），固定死。

- 如果是【插值放大一张位图】：原图只有 2048×1280 像素信息，放大后需要猜新像素 → 糊
- 如果是【矢量 UI 布局 + 坐标换算】：文字、按钮、窗口边框是矢量绘制指令，Windows 是**按新的物理尺寸重新渲染一遍**，不是拉伸现成图片 → 依然锐利！ 这就是为什么 DPI 缩放后的桌面文字、图标不会像改分辨率那样发糊。

#### 显示分辨率（显卡输出分辨率）

**情况 1：像素数量不一样，但是【宽高比例一样】**
举例： 面板原生：3072×1920（3:2） 显卡输出：1920×1280（也是 3:2） 像素数量更少，比例相同。 显示器 Scaler 芯片：**等比例放大**，把 1920×1280 均匀拉伸铺满 3072×1920 面板。 👉 画面不会压扁拉长变形，但是因为是插值补像素，**变糊**。

**情况 2：像素数量不一样 + 宽高比例也不一样**
举例： 面板原生：3072×1920（3:2） 显卡输出：1920×1080（16:9） 👉 比例不一样！显示器硬件缩放芯片有三种选择：
1. **等比例 + 黑边（信箱模式）**：保持画面不变形，上下留出黑条，画面完整，不变形，但是屏幕没有填满；
2. **等比例 + 裁切**：放大画面，把画面上下切掉一部分，填满整个屏幕，画面不变形，但是内容丢失；
3. **直接拉伸（不等比例缩放）**：强行把 16:9 的图拉到 3:2，画面压扁或者拉长，人物变形。

> 重点：**这个是显示器硬件层面的处理，是显卡输出信号到达显示器之后，显示器芯片做的事。** Windows 的【显示分辨率】只负责告诉显卡：你渲染多大一张图；**不负责决定显示器是裁边、黑边还是拉伸**，这个策略是显示器固件决定的，不同显示器设置不一样。

> 小结： 修改【显示分辨率】，改变的是**显卡输出图像的像素尺寸**； 显示器收到这张图，负责映射到自己物理像素上，数量 / 比例不匹配，就会触发显示器硬件缩放。



#### DPI 缩放：Windows 的「虚拟放大」

程序：我要画一个 `100逻辑px` 的按钮 Windows DPI 子系统：`100 × 1.5 = 150 物理px` 交给显卡：在画面里，画一个占 150 个真实像素的按钮。---显卡进行输出的时候就将像素点变多



#### 为什么DPI 可能坑 OBS

**不会被影响的程序：**

```text
现代程序 → 直接渲染 3072×1920 物理像素
→ OBS窗口捕获拿到原图
→ OBS缩放到1920×1080，只做一次缩放，画质可控
```


**会被DPI影响的老程序：**

```text
老程序（非DPI感知）→ 只渲染 2048×1280（逻辑尺寸位图）
→ Windows：插值放大到3072×1920（这一步产生模糊！）
→ OBS窗口捕获：拿到这张已经放大糊掉的图
→ OBS再缩放到1920×1080画布，二次缩放，画质进一步损失
```

- 非 DPI 老程序：画了一张小照片（2048×1280），Windows 先把这张小照片用画图工具拉大贴到墙上（插值、变糊），OBS 过来拍照，拍的是墙上已经拉大糊掉的照片。
- DPI 感知程序：直接按墙的大小画好完整大图（3072×1920）贴墙上，OBS 直接拍原图。
- 显示器捕获：直接对着整面墙拍照，不管墙上每一块是怎么贴上去的。

Windows 为了让老软件（截图工具、旧捕获器）正常显示，它给捕获 API 返回的，是**已经插值放大后的窗口副本（3072 对应尺寸）**，而不是原始 2048。 👉 这就是我们前面说的：OBS 拿到放大糊掉的 W。 这个放大副本，是 DWM 专门为了兼容老捕获工具**临时生成的一份拷贝**，不是全局桌面缓冲区里抠出来的。

#### 缩放导致画面变糊

链路：

1. 原图 A：\(2048\times1280\)（老程序原生渲染，这是原始细节来源）
2. 第一次缩放（放大，Windows）：\(2048\times1280 \Rightarrow 3072\times1920\) → 得到图 B
3. 第二次缩放（缩小，OBS）：\(3072\times1920 \Rightarrow 1920\times1080\) → 得到最终图 C

我们对比两种方案：

- 方案①（糟糕，上面这条）：**先放大，再缩小**，两次重采样
- 方案②（理想）：直接从原始 A \(2048\times1280\) 一步缩到 \(1920\times1080\)，只一次重采样



## 推流服务

所有这些地址、密钥，本质就是一套「地址 + 身份凭证」


|概念|类比|是否必须|
|---|---|---|
|RTMP 协议|通信语言（普通话）|✅ 必须，两端协议一致|
|推流服务器地址|驿站地址|✅ 必须，知道发到哪台机器|
|推流码（串流密钥）|房间号 + 开门密码|✅ 必须，身份校验 + 绑定直播间|
|完整推流 URL|驿站地址 + 房间号|✅ 合并后的完整目标|
|OBS 平台预设|预制好的驿站地址模板|❌ 可选，只是方便，自定义也能填|
- 服务地址不会发生变化，但是每一次直播，推流码会发生变化

## 视频编码

**硬件编码：**

显卡内部自带一块**专门用来压缩视频的独立硬件电路**（编码器），不依靠 CPU 通用计算，专门做 H.264 / HEVC / AV1 视频压缩。 常见硬件编码器：

- **NVENC**：NVIDIA 显卡（RTX/GTX）内置，目前直播首选硬编
- **AMF（VCE）**：AMD 显卡内置
- **QSV（Quick Sync）**：Intel 核显内置

**软件编码：**

完全交给 CPU 用通用算法程序去压缩画面，没有专用硬件电路



**编码资源消耗对比：**

|项目|软件编码 x264|硬件编码 NVENC（NVIDIA）|
|---|---|---|
|执行载体|CPU 通用计算核心|显卡内独立专用硬件编码电路（NVENC）|
|实现方式|软件代码，逐条 CPU 指令运算|硬件流水线 ASIC，电路直接实现编码算法|
|运动估计|CPU 暴力软件搜索，搜索范围可自由调（preset）|硬件内置搜索单元，搜索策略固定，可调空间小|
|CPU 开销|高（10%~60%，视分辨率 / 帧率、preset）|极低（通常 <5%）|
|GPU 3D/CUDA 开销|几乎无|几乎无，只占用独立 NVENC 单元|
|画质潜力|上限高，慢预设下同码率画质最好|新显卡很好，老显卡弱；上限略低于顶级 x264|
|延迟|略高（依赖 CPU 调度）|更低，流水线硬件处理|
|并发限制|CPU 性能决定，想开多少路看 CPU|硬件通道数量锁死（2 路居多）|
|典型适用|CPU 富余、录播、追求极致画质、显卡没有硬编单元|游戏直播、CPU 紧张、不想游戏掉帧（主流选择）|





# 直播姬配置

**画面源采集：**
- 优先【游戏捕获】：直接读取游戏渲染缓冲区，性能最低，画质最好
- 尽量不要窗口捕获，资源开销更大



**Windows 系统前置设置（必须先做）**

1. 右下角喇叭右键 → 声音设置 → 更多声音设置
    - **播放（输出）默认设备：你的耳机**（游戏声音输出到耳机，你自己听）
    - **录制（输入）默认设备：你的耳机麦克风**
2. 【通信】标签页：选择 **不执行任何操作**

> 这个是经典坑：Windows 默认开了 “通话时自动压低其他音量”，一开麦游戏声音直接变小，直播里面声音忽大忽小



**直播姬音频设置（直播设置 → 音频）**

- **麦克风设备：选中【你的耳机麦克风】**（不要默认设备，手动锁定）
- **扬声器（系统声音）：选中【你的耳机】**（直播姬抓取耳机这条输出流，也就是游戏音效，送给直播间观众）


**总结一下上述配置：**

1. **Windows 层面的声卡默认设置，开播 / 不开播，一直是固定不变的** 播放默认 = 耳机、录制默认 = 耳机麦、通信选项 = 不执行任何操作。 这个是**系统底层路由**，和直播姬开没开播毫无关系，就算直播姬完全关掉，这套设置也保持原样。 你打游戏、语音、听歌，都走这套通路。
2. 直播姬只是一个**采集 + 转发的消费者**： 它不会修改 Windows 声卡的默认路由，它只是**选定这两个设备作为它自己的输入源**：

- 拿耳机麦 → 拿你的人声
- 抓取耳机这条输出流 → 拿到游戏声音
