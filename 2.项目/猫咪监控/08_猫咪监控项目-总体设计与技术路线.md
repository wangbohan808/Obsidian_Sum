# 08 猫咪监控项目：总体设计与技术路线

> 前置：已掌握文档 00~07（四套镜像构建方法 + RKNN/RKLLM 端侧 AI）。
> 本文档把前七篇学到的能力收敛到**一个真实可落地、可写进简历**的项目：
> ROCK 5C + 摄像头 + 端侧 AI，实现"只录猫咪进食/饮水"的智能监控。

---

## 1. 项目目标（一句话）

在 ROCK 5C（RK3588S2，6 TOPS NPU）上部署一个 24 小时运行的端侧视觉系统：

1. 摄像头对准**猫碗（进食区）**与**饮水机（饮水区）**；
2. 通过家庭 WiFi 联网；
3. 只有当 AI 判定猫咪**正在进食或正在饮水**时才录制视频；
4. 其余情况（路过、趴着、仅仅停留）**不录制**，避免产生海量无意义视频；
5. 视频先存本地，再自动上传到**家庭局域网主机**或**云盘**；
6. 最终把整套软件做成**只含所需驱动 + 端侧 AI 的最简发行版镜像**。

## 2. 需求拆解

### 2.1 功能需求

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F1 | 持续采集画面 | 7×24 小时稳定运行，掉线自动恢复 |
| F2 | 猫咪检测 | 能稳定检测到画面中的猫（大小、遮挡、夜间） |
| F3 | 行为识别 | 区分：进食 / 饮水 / 靠近但不进食（停留）/ 无猫 |
| F4 | 事件录制 | 判定"进食/饮水"才开始录，事件结束自动停录 |
| F5 | 预录与续录 | 事件前保留 5~10 秒预录，行为中断 10 秒内续录（防抖动） |
| F6 | 视频存储 | 本地按日期/事件分类保存，H.264/H.265 硬件编码 |
| F7 | 上传 | 局域网 SMB/NFS 或云盘（rclone/WebDAV/OSS）定时上传 |
| F8 | 通知（加分项） | 事件发生时推送通知（钉钉/微信/Bark Webhook） |
| F9 | 最简发行版 | 最终镜像只含本项目所需驱动与软件，可烧录即用 |
| F10 | 本地常显屏（可选） | 猫区旁常亮「相框+看板+氛围+告警」；标定不上屏；无屏镜像主服务仍可独立运行（见文档 16） |

### 2.2 非功能需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| N1 | 低误录率 | 因"停留"而误录的视频占比 < 10% |
| N2 | 实时性 | 单帧 AI 推理 < 50ms（640 输入），端到端事件响应 < 2s |
| N3 | 资源占用 | NPU 负载可控、CPU 平均 < 40%（8 核）、不因录制卡顿 |
| N4 | 可靠性 | 断电自动恢复、存储满自动清理、断网自动重连并补传 |
| N5 | 可复现 | 镜像构建、模型转换、应用部署全部脚本化、文档化 |

## 3. 总体架构

```text
┌──────────────────────── ROCK 5C（RK3588S2）────────────────────────┐
│                                                                    │
│  摄像头（USB UVC 或 MIPI CSI）                                      │
│     │  V4L2 / Media-Controller（驱动层）                            │
│     ▼                                                              │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ 采集与预处理：rkcif/rkisp（MIPI）或 UVC → RGA 缩放/色彩转换   │   │
│  └─────────────────────────────────────────────────────────────┘   │
│     │ 低帧率抽帧（如 10fps）                                        │
│     ▼                                                              │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │ ① 运动门控（帧差法，CPU 极轻量）→ 有运动才进 NPU             │   │
│  │ ② 猫咪检测（YOLOv8n 单类，RKNN INT8）→ 猫框 + 头部关键点     │   │
│  │ ③ 行为判定（头部在"碗区/水区 ROI"内且持续 → 进食/饮水）      │   │
│  │ ④ 时序状态机（IDLE/CANDIDATE/ACTIVE/COOLDOWN + 迟滞）        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│     │ 事件触发                                                     │
│     ▼                                                              │
│  GStreamer（v4l2src → mpph264enc 硬件编码 → mp4）                  │
│     │                                                              │
│     ├─► 本地存储 /data/videos/YYYY-MM-DD/eat_*.mp4 / drink_*.mp4   │
│     └─► 上传器（SMB/NFS 挂载 + rsync，或 rclone → 云盘）           │
│                                                                    │
│  systemd 服务：cat-camera.service / cat-upload.timer / watchdog    │
└────────────────────────────────────────────────────────────────────┘
```

## 4. 硬件选型

| 部件 | 推荐 | 理由 |
| --- | --- | --- |
| 开发板 | ROCK 5C（RK3588S2，4/8GB） | 6 TOPS NPU 足够跑 YOLOv8n；板载 WiFi6/BT（AIC8800D80）；千兆网口；eMMC+TF+PCIe |
| 摄像头（方案 A，首选） | USB UVC 摄像头（1080p/30fps，广角） | 免 MIPI 驱动移植，V4L2 即插即用，开发最快；建议带红外夜视或补光灯 |
| 摄像头（方案 B，进阶） | Radxa Camera 8M 219（IMX219）或 Camera 4K（IMX415），走 4-lane MIPI CSI | 图像质量高、延迟低、功耗低；需要自建 DTS overlay（见文档 09），适合展示 BSP 功底 |
| 存储 | 32GB+ 高速 microSD（开发）→ eMMC 或 FPC PCIe NVMe（长期） | 视频落盘带宽要求低（1080p H.264 约 1~3 GB/天），NVMe 更耐久 |
| 电源 | 5V/3A+（官方推荐 30W PD） | 24 小时稳定供电 |
| 网络 | 家庭 WiFi（2.4G/5G）或千兆有线 | WiFi 需求按项目要求；有线更稳，可双冗余 |
| 散热 | 官方散热片/小风扇 | 长时间 7×24 运行，避免 NPU 满载过热降频 |

> 相机摆放建议：距猫碗 1~1.5 米、略高于桌面俯视 15~30°，保证猫头部与碗在同一画面；避免逆光与强背光，夜间开补光灯或选红外摄像头。

## 5. 技术栈清单（对应简历关键词）

### 5.1 构建与系统层

- BSP 工具链：定制 U-Boot、内核（驱动裁剪、设备树、补丁固化）
- 镜像构建三/四条路线：Yocto（bitbake/recipe/layer）、Buildroot（rk3588_sdk）、rsdk（RadxaOS 组装）、BSP deb 集成
- systemd 服务管理、watchdog、overlayfs 只读 rootfs（可选）、内核模块裁剪

### 5.2 驱动与媒体层

- V4L2 / Media-Controller / v4l2-subdev / videobuf2（UVC、MIPI CSI-2）
- RK ISP/CIF（rkcif、rkisp、rkispp）——MIPI 方案
- GStreamer + rk mpp 硬件编码（mpph264enc / mpph265enc）、RGA 硬件缩放、VEPU 视频编码单元
- ALSA（可选音频事件融合）

### 5.3 端侧 AI 层

- RKNN-Toolkit2（PC 端转换/量化）→ RKNN-Lite2 / RKNN Runtime（板端推理）
- YOLOv8n / YOLOv8n-pose 检测 + 头部关键点；小型分类器（MobileNetV3 等）
- 模型优化：INT8 量化、校准集、蒸馏/剪枝（可选项）、输入分辨率与帧率调优、NPU 多核/零拷贝

### 5.4 应用与运维层

- Python（numpy/opencv）+ C/C++（RKNN Runtime）混合
- 事件状态机、时间戳命名、预录/续录缓冲
- rsync / SMB / NFS / rclone（WebDAV、OSS、网盘）
- 日志轮转、健康自检、断网补传、Webhook 通知

### 5.5 本地常显屏（可选，文档 16）

- Qt 5 Widgets 交叉编译（linuxfb/eglfs），与无头主服务分进程
- Unix Domain Socket + JSON Lines 状态推送；精彩帧 JPEG 相框池
- 场景优先级：告警 > 正在发生 > 访客 > 仪式 > 日记 > 夜间 > 相框
- 产品原则：情趣/家庭看板为主，不做 ROI 调参 GUI

## 7. 四条构建路线在本项目中的分工

| 路线 | 在本项目中的角色 | 最终是否使用 |
| --- | --- | --- |
| BSP（bsp） | 定制内核：开启/裁剪驱动（UVC、rkcif/rkisp、rknpu、MMC、WiFi），输出 linux-image deb | ✅ 必用（定制内核） |
| rsdk | 主推：用 Debian rootfs 组装最终镜像，`--debs` 集成 BSP 内核与自研包 | ✅ 主推（开发最快、AI 生态全） |
| Buildroot（rk3588_sdk） | 备选：产出几十 MB 级极简固件，展示"最小镜像"能力 | ⭕ 备选（量产/演示用） |
| Yocto | 进阶：把整套系统固化为可复现的 recipe 流水线 | ⭕ 进阶（简历加分项） |

## 8. 技术方案的关键决策与理由

| 决策 | 选项 | 本项目选择 | 理由 |
| --- | --- | --- | --- |
| 摄像头接口 | USB UVC vs MIPI CSI | USB UVC 起步，MIPI 作为进阶 | USB 开发快、风险低；MIPI 展示驱动功底、适合长期部署 |
| 检测模型 | YOLOv8n vs YOLOv8s 等 | YOLOv8n（单类 cat） | NPU 友好（约 3.2M 参数），INT8 后单帧 <30ms |
| 行为判定 | 纯分类器 vs 检测+ROI 规则 | 检测 + 头部关键点 + ROI 规则为主，可选小分类器融合 | 可解释、样本需求小、误判可控；分类器做鲁棒性兜底 |
| 是否用大模型 | RKLLM（本地问答） vs 不用 | 本项目不用；RKLLM 作为选修演示 | 猫监控实时性要求高，LLM 无必要；预留 RKLLM 能力说明 |
| 录制编码 | 软件编码 vs MPP 硬件编码 | MPP H.264（1080p/15fps） | 编码几乎零 CPU，功耗低，稳定 |
| 上传 | 实时推流 vs 事件后传 | 事件视频先落盘，再批量上传 | 简单可靠、断网可补传；实时推流 RTSP 作为加分项 |
| 镜像方案 | rsdk vs Buildroot | rsdk 主推 | Debian 生态与 AI 包安装最省力（详见文档 04/06） |
