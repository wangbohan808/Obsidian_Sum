# 规格漂移与例外管理

> [!info] 一句话定义
> AI 忘掉的不是"你说过的约束"，而是**"哪个是标准、哪个是例外"**——因为从来没告诉过它这个区别，而在代码里两者的长相、字节数、权重完全一样。
>
> 标准 A → 工位 N 特殊化成 B（且已批准）→ 新工位 N+1 默认套了 B。这件事的学名叫**规格漂移（specification drift）**，例外把标准挤掉的过程叫**例外污染（exception contamination）**。

## 一、为什么"前面强调过的约束"必然失效

不是提示词不够狠，是三条机制同时作用，且每一条都独立成立。

### 1. 上下文窗口是滑动的，先说过的必然滚出去

你在第一轮说"所有工位按标准 A 走"，到了第 40 轮，那句话要么已经滚出窗口，要么被有损压缩成一句摘要。**只要约束住在对话里，它的寿命就由 token 数决定，与你的强调程度无关。** 强调一次只是提高它在窗口内的存活概率，不是让它永久驻留。

推论：**任何只存在于对话里的约束，都在倒计时。**

### 2. AI 真正反复读到的是代码，而代码里标准和例外是平权的

对话是一次性的，代码是每一轮都要重读的现场。于是真正塑造输出的不是你说的话，是**它眼前看到的最像的那个实现**。

问题在于：标准实现出现一次，例外实现也出现一次。**在模式匹配眼里，它们分量相同。** 而例外通常更新、更近、还带着"这是能跑通的最终版"的光环。

> 就近原则 > 权威原则。AI 找的不是"最新的规范"，是"最近的相似代码"。

### 3. 你说的"这个特殊工位没问题"，是一次合法的降级授权

这是整件事最隐蔽的一刀。

人类语境里，「强调一下这个特殊工位没问题」= **批准一次带作用域的豁免**。
AI 语境里，它被解析成 = **这种写法是合法的、被认可的**。

**豁免没绑定作用域，就等于把例外提拔成了新标准。** 你以为你在说"仅此一处"，它收到的是"此法可用"。而且它不会错——因为它确实收到了你的许可，只是没收到边界。

## 二、症状清单：对号入座

| 你看到的现象 | 真实原因 |
|---|---|
| 新工位继承了上个特殊工位的逻辑 | 例外没绑定作用域，被当成通用写法 |
| 越往后改越乱，最后不敢动 | 例外散落在主代码里，没有隔离，改一处牵连全部 |
| 每次开新对话都要重讲一遍规则 | 约束没有外置，住在对话里 |
| AI 说"参考了工位 A-3 的实现" | 就近匹配，它没被告知 A-3 是例外 |
| 同一个需求两个工位实现不一样，都没报错 | 缺少可执行的契约，"对不对"没有判定器 |

## 三、解法：六层，按有效性排序

### 第 1 层（最有效）默认值反向：标准是 fallback，例外是白名单

这一层单独就能挡住 80% 的问题。

```js
// ✗ 错：标准 + 特例改写。新工位不在任何分支里 → 落到哪个看运气
if (station === 'A-1') { std() }
else if (station === 'A-2') { std() }
else if (station === 'A-3') { special() }   // 例外
else { std() }                              // 全靠最后这个 else 兜底

// ✓ 对：标准是默认分支，例外是显式集合
const EXCEPTIONS = { 'A-3': specialHandler }   // 全项目唯一的例外清单
const handler = EXCEPTIONS[station] ?? stdHandler
```

关键差别：**新工位默认不进白名单，所以自动落标准，不需要任何人记得它。**

用 `if (station in SET)` 而不是 `if (station === 'A-3')`。前者是声明"世界由标准和例外组成"，后者是打补丁——补丁永远补不完，声明只需要维护一张表。

### 第 2 层 物理隔离：例外不许住在标准文件里

上一层的漏洞是：例外代码仍在主文件中，AI 一读就看见，照样模仿。

所以例外工位的实现放**独立文件**，主文件只留一个薄注册表：

```
src/
  station/
    standard.js        ← 标准实现。永远只有这一份，永远是对的
    exceptions/
      a3.js            ← 例外。文件名就写着它是例外
      registry.js      ← 唯一的例外清单，8 行以内
```

**理由：AI 的模式匹配依赖"可见性"，看不见的代码就无法被模仿。物理隔离比逻辑分支可靠得多。** 逻辑分支靠它读懂了才生效，文件隔离是它根本没读到。

### 第 3 层 例外必须登记，且登记的是"作用域 + 依据 + 到期"

代码里：

```js
// DEVIATION: station=A-3 | 依据: 工单 #1234 | 原因: 该工位夹具偏移 2mm | 复核: 2027-01-01
```

同时仓库根目录一份 `EXCEPTIONS.md`：

| 工位 | 偏离哪条标准 | 原因 | 依据 | 批准 | 复核日期 |
|---|---|---|---|---|---|
| A-3 | 取料高度 12mm → 10mm | 夹具偏移 2mm | #1234 | — | 2027-01-01 |

**判据简单粗暴：新工位不在这张表里 → 就是标准，没有第三种可能。** 这句话让"忘不忘"从一个记忆问题变成了一个查表问题。

### 第 4 层 新建实例禁止 copy-paste

复制已有工位代码来新建工位，是**例外污染的高速公路**——你复制的到底是标准还是上一处例外，取决于你手点的是哪个文件。

规则：
- 新建工位只允许从 `station/template/` 生成，模板里只有标准；
- 给 AI 的指令要写成 **"参考 `standard.js`，忽略 `exceptions/` 目录下的一切"**，而不是"参考 A-1 工位"；
- A-1、A-2 这类"普通工位"也不要存在多份拷贝——它们本身就是标准的副本，副本越多，哪个是原件越说不清。

### 第 5 层 标准写成可执行测试

文档会被忘，注释会被跳过，**测试不会**——它跑不过就是跑不过。

- 每个标准行为一条契约测试，新工位必须全绿才算接入；
- 例外工位额外跑一组"例外用例"，并**明确断言它在哪一点上故意偏离标准**（这条测试同时也是例外的一份活文档）；
- 一旦有人无意间把例外逻辑推广到新工位，契约测试会立刻红。

测试是标准的**可执行版本**，也是唯一不依赖任何人记性的版本。

### 第 6 层 约束搬进仓库，别留在对话里

| 文件 | 给谁 | 放什么 |
|---|---|---|
| `AGENTS.md`（通用）/ `.cursor/rules/*.mdc` / `CLAUDE.md` | AI，每次会话自动读 | 项目标准、目录约定、例外表指针、"新建实例禁 copy-paste" |
| `EXCEPTIONS.md` | 人和 AI 共用 | 唯一例外清单 |
| `spec.md` | 人 | 为什么这样设计、标准从哪来 |

规则文件要**分层写清权威等级**，否则 AI 遇到冲突时会随机挑一条：

```md
## 规则的优先级（冲突时按序号）
1. 安全 / 不动硬件（铁律）
2. 本文件《标准》
3. EXCEPTIONS.md 中的豁免（仅在表列工位内生效）
4. 本次任务的临时指令
```

**第 3 条那句"仅在表列工位内生效"是整份文件里最重要的一行。** 少了它，豁免就会外溢。

## 四、AI 侧操作协议：开工三句话

对话约束会过期，但**协议**不会——因为它每次都被重新执行。

**开工前**（强制 grounding，把规则从文件里读出来，而不是指望它记得）：
> 读 `AGENTS.md` 和 `EXCEPTIONS.md`。先用 5 条复述本项目标准，再回答：本工位是否在例外表内？在表内，豁免的是哪一条？

**生成中**（把豁免变成必须交付的产物）：
> 任何偏离标准的写法，必须同时给出三样：① `DEVIATION` 注释 ② `EXCEPTIONS.md` 新条目 ③ 一条锁定该偏离的测试。缺任何一样，一律按 bug 处理。

**提交前**（逼它自己报漂移）：
> 列出本次改动中偏离标准的每一处，逐条说明作用域和依据。如果某处只对单个工位成立，说明它为什么不能进标准。

第二句是核心：**"豁免"从一句口头许可，变成了三份必须落地的产物。没有产物，就没有豁免。**

## 五、一条反向判断：例外多到某个数，是标准错了

例外本身不是罪——现实里工位确实会有差异。但**例外累积到 3~5 个，且反复围绕同一个点，说明标准本身过时了**，这时候该做的是把标准升一级（比如把取料高度做成配置项），而不是继续加白名单。

判据：
- 例外**围绕不同点**，每条独立 → 正常的现实差异，继续登记；
- 例外**围绕同一个点** → 那个点本来就不该是硬编码标准，它是参数，不是规则。

**这和第 3 层不冲突**：登记是为了让漂移可见，可见之后才能判断该收缩还是该演进。看不见的例外既不能被遵守，也不能被分析。

## 六、为什么这套东西成立（底层同构）

这就是运维里的 **configuration drift**，换了个主语：

| 传统运维 | AI 编码 |
|---|---|
| 服务器配置靠人手工改 | 代码靠多轮对话生成 |
| 时间一长，机器之间不一致 | 时间一长，工位实现不一致 |
| 解法：IaC（配置即代码）+ 漂移检测 | 解法：SSOT（标准即文件）+ 契约测试 |
| 例外要审批、要留痕、要有回收日期 | 例外要登记、要绑作用域、要复核日期 |

**本质是同一个问题：只要"默认状态"没有唯一维护点，任何长链路的复制都会漂。** 生成式开发没制造这个病，它只是把"人会忘"换成了"模型会忘"，并且把周期从几个月压到了几小时。

推论也就一样：**不要试图靠"更认真地记住"来治它**。人记不住，模型也记不住，两者的补救方式都是把默认值写到机器必须读的地方去。

## 七、最小可落地版本（今天就做三件）

如果只做三件事：

1. 仓库根目录建 `AGENTS.md`，写 5 条标准 + 一行"新建工位禁 copy-paste，只从 standard 生成"；
2. 把所有例外收进一个 `EXCEPTIONS` 常量 / `exceptions/` 目录，主代码改成 `?? std` 兜底；
3. 每条标准写一条测试，新工位接入前必须全绿。

做完这三件，**"新工位默认走标准"就不再依赖任何人记得**——它变成了代码结构、文件布局和 CI 的必然结果。

## 八、检查清单

- [ ] 标准写在仓库文件里，还是在对话/脑子里？
- [ ] 主代码的默认分支是标准，还是靠一串 `else if` 兜底？
- [ ] 例外是"集合 + 白名单"，还是散落的 `=== 'A-3'`？
- [ ] 例外代码是否与标准实现物理隔离？
- [ ] `EXCEPTIONS.md` 里每条例外有作用域、依据、复核日期吗？
- [ ] 新建实例是从模板生成，还是从别的实例 copy？
- [ ] 每条标准有测试吗？例外有"它故意偏离标准"的断言吗？
- [ ] 例外是否围绕同一个点堆积（→ 该改标准了）？
